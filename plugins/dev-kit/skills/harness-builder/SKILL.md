# Harness Builder

AI가 코드를 쓰는 프로젝트에서 지켜야 할 것을 문서가 아니라 검사로 지키게 하는 스킬이다. 규칙을 글로 적어 두면 어겨도 아무 일이 없지만, 검사로 걸어 두면 어긴 커밋이 실패한다. 이 스킬은 그 검사를 프로젝트에 세우고, 세운 검사가 실제로 막는지까지 확인한다.

특정 스택을 설치하는 스킬이 아니다. 조건은 스택과 상관없이 같고, 조건을 채우는 도구만 스택마다 다르다.

## 핵심 원칙

- **조건은 고정이고 도구는 고른다.** 무엇을 갖춰야 하는지는 이 문서가 정한다. 어떤 도구로 갖출지는 아래 순서로 정한다. 조건을 채울 수 있는 도구일 때만 쓰고, 채울 수 없으면 다음 순서로 넘어간다.
  1. 프로젝트가 이미 쓰는 것
  2. 뼈대가 기본으로 주는 것
  3. 스택 파일의 추천

  "2. 고르기"에서 묻는 항목은 사람이 고른 것을 쓴다.
- **확인받기 전에는 아무것도 바꾸지 않는다.** "할 일" 화면에서 진행을 고르기 전에는 파일을 쓰지 않고, 설치하지 않고, 폴더를 만들지 않는다.
- **이미 있는 설정은 덮어쓰지 않는다.** 없으면 더하고, 같으면 두고, 다르면 보여 주고 사람이 고르게 한다.
- **깔았다고 끝내지 않는다.** 조건마다 위반 예시와 통과 예시를 넣어 검사가 실제로 막고 통과시키는지 본다.
- **검사를 약하게 만들지 않는다.** 기존 코드가 검사에 걸려도 규칙을 끄거나 예외를 더하지 않는다. 걸린 것은 고치지 않고 보고한다.
- **커밋하지 않는다.** 바꾼 파일은 작업 트리에 남긴다.

## 조건

필수 조건은 어기면 커밋이 실패해야 한다. 권고는 경고만 낸다.

| 묶음 | 조건 | 뜻 |
|---|---|---|
| Project | git 저장소 | 프로젝트 폴더가 git 저장소다 |
| Project | 코드 모양 통일 | 포매터가 있고 커밋할 때 자동으로 적용된다 |
| Project | 정적 검사 | 린터가 있고, 필수 조건에 해당하는 규칙은 위반하면 실패한다 |
| Project | 타입 검사 엄격 | 타입 검사가 엄격 모드로 돈다 |
| Project | 테스트 도구 | 로직 테스트를 돌릴 도구가 있다 |
| Project | 명령 이름 | 검사, 테스트, 실행 명령이 프로젝트의 정해진 자리에 이름으로 있다 |
| Project | 커밋 전 검사 | 커밋하면 포맷, 정적 검사, 타입 검사, 바뀐 파일과 관련된 테스트가 돈다 |
| UI | 컴포넌트 자리와 데이터 자리 | 화면 조각을 두는 폴더와, 서버 호출·저장·도메인 로직을 두는 폴더가 정해져 있다 |
| UI | 컴포넌트의 서버 호출·저장 금지 | 컴포넌트 자리의 파일이 서버를 부르거나 저장소를 직접 쓰면 실패한다 |
| UI | 컴포넌트와 데이터의 분리 | 컴포넌트 자리의 파일이 데이터 자리의 파일을 직접이든 다른 파일을 거쳐서든 가져오면 실패한다. 타입만 가져와도 실패한다 |
| UI | 접근성 | 접근성 규칙을 위반하면 실패한다 |
| UI | 미리 볼 자리 | 컴포넌트를 앱 로직 없이 띄워 볼 자리가 있다 |
| UI | 화면 찍기 | AI가 화면을 이미지로 찍을 수단이 있다 |
| AI | 검사 건너뛰기 금지 | AI가 커밋 전 검사를 건너뛰는 커밋을 하면 막힌다 |
| AI | 검사 설정 보호 | AI가 파일 수정 도구로 검사 설정 파일을 고치려 하면 사람에게 확인 창이 뜬다 |
| Recommended | 토큰만 쓰기 | 컴포넌트에 색, 글꼴, 간격 값을 직접 쓰면 경고가 뜬다 |

- UI 묶음과 Recommended는 화면이 있는 프로젝트에만 적용한다. 화면이 없는 프로젝트(CLI, 라이브러리, 서버)에서는 대조와 화면에서 뺀다.
- 조건끼리 기대는 것이 있다. "컴포넌트의 서버 호출·저장 금지", "접근성", "토큰만 쓰기"는 "정적 검사"에, "컴포넌트와 데이터의 분리"는 "컴포넌트 자리와 데이터 자리"에, 실패로 막는 모든 조건은 "커밋 전 검사"에 기댄다. 기대는 조건을 건너뛰면 그 위의 조건도 함께 건너뛴다.

### 스택 파일

스택마다 달라지는 것(추천 도구, 조건마다 꼭 지켜야 하는 것, 위반 예시가 담아야 하는 것)은 `${CLAUDE_SKILL_DIR}/references/stacks/`의 스택 파일에 있다. 어느 파일을 읽을지는 파일 맨 위의 frontmatter로 정한다.

- `kind`: `language`는 그 언어의 프로젝트면 무엇을 쓰든 같은 것을, `library`는 그 라이브러리를 쓰면 프레임워크와 상관없이 같은 것을, `framework`는 그 프레임워크라서 달라지는 것을 담는다.
- `when`: 기존 프로젝트에서 이 스택임을 알아보는 표시다. 맞는 파일을 모두 읽는다.
- `base`: 이 파일이 기대는 파일이다. 끝까지 따라가며 모두 읽는다. 기대는 쪽 파일은 다른 점만 적으므로 함께 적용한다.
- `for`: 새 프로젝트에서 이 프레임워크로 만들 수 있는 "만드는 것"이다. 같은 `for`의 파일 가운데 `recommended: true`인 파일이 추천값이고, `reason`이 그 이유다.
- 고른 프레임워크의 파일이 없어도, 그 프레임워크가 쓰는 언어와 라이브러리의 파일이 있으면 읽는다.

스택 파일은 설정 파일의 문법, 옵션 이름, 설치 명령을 적지 않는다. 도구의 버전마다 달라지기 때문이다. 괄호 안에 적힌 옵션 이름은 확인한 날 기준의 예다. 이런 것은 기억으로 쓰지 않고 아래 순서로 확인한다.

1. 프로젝트에 설치된 것: 패키지 안에 든 문서, 도구의 `--help`, 적용된 설정을 보여 주는 명령
2. 그 도구의 공식 문서

맞는 스택 파일이 없는 스택이나 도구는 "확인 안 된 조합"이다. 조건과 확인 방법은 똑같이 적용하고, 스택 파일이 정해 주던 것은 [references/stack-template.md](references/stack-template.md)의 틀을 따라 그 스택의 공식 문서에서 찾는다. 화면과 보고에 "확인 안 된 조합" 줄로 알린다.

## 안내 언어와 형식

사용자에게 보여 주는 글은 한국어로 쓴다. 화면의 묶음 이름(`Project`, `UI`, `AI`, `Recommended`)만 영어로 쓴다.

질문, 화면, 보고는 이 문서의 템플릿을 따른다.

- 틀: 첫 줄, 상태 이모지, 조건 수를 세는 줄, 묶음 이름, 번호 선택지의 번호·이름·순서, `다음:` 줄, 질문의 문장. 사람과 부른 AI가 이것으로 읽고 답하므로 바꾸지 않는다. 질문의 문장은 `<…>` 자리만 채우고 말투를 바꾸지 않는다.
- 모양: 들여쓰기, 빈 줄, `→` 뒤의 설명은 자유롭게 쓴다. 설명은 한 줄로 쓴다.
- "있을 때만" 줄은 해당할 때만 쓰고, 없으면 줄째 뺀다.
- 질문, 화면, 보고는 템플릿 자체가 응답 전체다. 앞뒤에 문장을 덧붙이지 않고, 코드 블록(```)으로 감싸지 않는다.
- 질문은 한 번에 하나만 한다.
- `다음:` 줄은 스킬이 끝난 뒤 읽는 쪽이 할 행동이다. 질문이 아니며, 스킬은 답을 기다리지 않는다.

상태 이모지는 네 가지다. 보고에서만 ❌를 더 쓴다.

| 이모지 | 뜻 |
|---|---|
| ✅ | 충족. 이미 갖춰져 있다 |
| ➕ | 추가. 이 스킬이 설치하거나 설정한다 |
| ⚠️ | 충돌. 기존 설정이 조건과 달라 사람이 고른다 |
| ⏭ | 건너뜀. 사람이 고르지 않았거나, 기대는 조건을 건너뛰었다 |
| ❌ | 실패. 설치했지만 확인에서 막지 못했다 (보고에만) |

자동 모드는 없다. 무엇을 쓸지와 기존 설정을 바꿀지는 사람이 정하는 일이기 때문이다. 다른 스킬이나 AI가 불러도 2번과 3번의 확인은 사람에게 그대로 묻는다.

### 1. 살펴보기

읽기만 한다. 아래를 파악한다.

- 새 프로젝트인지 기존 프로젝트인지. 프로젝트 정의 파일(`package.json`, `pubspec.yaml`, `Cargo.toml` 등)이 없으면 새 프로젝트다.
- 기존 프로젝트면 앱 이름, 프레임워크, 패키지 매니저(잠금 파일로), 테스트 도구, 스타일 방식, 화면이 있는지
- 스택 파일들의 frontmatter
- 이 컴퓨터에 깔린 패키지 매니저
- git 저장소인지, 커밋 안 된 변경이 있는지
- 요청에 이미 들어 있는 답 (앱 이름, 만드는 것, 프레임워크, 도구)

### 2. 고르기

아래 항목을 위에서부터 정한다. 요청에 답이 있거나 프로젝트에서 찾은 항목은 묻지 않고, 나머지는 하나씩 묻는다. 새 프로젝트는 찾을 것이 없으므로 요청에 없는 항목을 모두 묻게 된다.

| 순서 | 항목 | 묻는 때 |
|---|---|---|
| 1 | 앱 이름 | 새 프로젝트 |
| 2 | 만드는 것 | 새 프로젝트 |
| 3 | 프레임워크 | 새 프로젝트 |
| 4 | 패키지 매니저 | 잠금 파일이 없을 때 |
| 5 | 테스트 도구 | 프로젝트에 없을 때 |
| 6 | 스타일 | 화면이 있고, 프로젝트에서 찾지 못했을 때 |
| 7 | 컴포넌트 자리와 데이터 자리 | 화면이 있고, 프로젝트에서 찾지 못했을 때 |
| 8 | 미리 볼 자리 | 화면이 있고, 프로젝트에 없을 때 |

앱 이름:

```
앱 이름을 알려 주세요.
앱은 지금 폴더(<폴더 이름>)에 만듭니다. 하위 폴더에 만들고 싶으면 함께 말씀해 주세요. 하위 폴더에 만들면 셋업이 끝난 뒤 그 폴더에서 Claude Code를 다시 열어야 AI 조건을 확인할 수 있습니다.
```

만드는 것:

```
무엇을 만드나요? 번호로 답해 주세요.
1. 웹 앱
2. 모바일 앱
3. 웹과 모바일 앱
4. 서버·API
5. CLI·라이브러리
```

4번이나 5번을 고르면 화면이 없는 프로젝트로 본다.

나머지 항목:

```
<항목>을 골라 주세요. 번호로 답해 주세요.
1. <추천값> (추천: <이유 한 줄>)
2. <대안>
3. 없음

다른 것을 쓰려면 이름을 말씀해 주세요.
```

- 질문은 한 번에 하나만 한다. 답을 받은 뒤 다음 항목을 묻는다.
- `<항목>을`의 조사는 항목 이름에 맞춘다. 예: `프레임워크를`, `테스트 도구를`, `스타일을`
- 첫 선택지는 추천값이다. 추천값은 스택 파일을 따르고, 스택 파일이 없으면 그 스택의 공식 문서를 찾아 정한다. 스택 파일에 없는 선택지에는 `(확인 안 된 조합)`을 붙인다.
- "프레임워크"의 선택지는 `for`가 "만드는 것"의 답과 같은 프레임워크 파일들이다. `recommended: true`인 파일이 첫 선택지이고 이유는 그 파일의 `reason`이다. 나머지 파일이 대안이다. 선택지의 이름은 그 파일의 제목(`#` 줄)이다.
- "프레임워크"에는 "없음"도 넣는다. 뼈대 도구 없이 시작한다는 뜻이다.
  - 화면이 있는 프로젝트는 마지막 선택지로 `없음 (확인 안 된 조합)`을 넣는다. UI 조건의 도구를 정해 주는 스택 파일이 없기 때문이다.
  - 화면이 없는 프로젝트는 "없음"이 첫 선택지(추천값)다. 이유에는 프레임워크 없이 만들 수 있다는 점을 쓴다. 대안은 그 종류의 프로젝트에 쓰는 프레임워크다. 마지막 선택지에 "없음"을 다시 넣지 않는다.
  - 고르면 되묻지 않고 아래 한 줄로 알린 뒤 다음 항목으로 넘어간다.

    ```
    프레임워크 없이 진행합니다. 뼈대 도구 없이 <언어 파일의 "뼈대"가 정한 것>부터 만듭니다.
    ```

- 프레임워크가 정해지면 뼈대 도구가 정한 위치에 만들 수 있는지 확인한다. 폴더가 비어 있어야 하는지, 폴더 이름에 제약이 있는지를 본다. 만들 수 없으면 이유를 알리고 하위 폴더에 만들지 묻는다.
- 뼈대 도구의 옵션은 사람이 고른 것과 조건에 필요한 것만 정하고, 나머지는 뼈대의 기본값을 따른다. 뒤 항목의 추천값도 그 기본값을 기준으로 낸다.
- 추천값 말고 대안을 하나 이상 넣는다. 사용자가 선택지에 없는 값을 말하면 그 값을 받는다.
- 스택 파일에 없는 값은 답을 받은 자리에서 쓸 수 있는지 확인한다. 그 도구의 공식 문서를 찾아 아래 세 가지를 본다.
  - 실제로 있는 도구인가
  - 앞에서 고른 항목과 함께 쓸 수 있는가
  - 이 컴퓨터에서 쓸 수 있는가
- 쓸 수 없으면 아래 한 줄로 알리고 같은 질문을 다시 한다. 쓸 수 있거나 문서로 판단할 수 없으면 받고, "고른 것" 화면의 "확인 안 된 조합"에 넣는다.

  ```
  <값> 쓸 수 없음 · <이유 한 줄>
  ```
- 패키지 매니저의 선택지는 이 컴퓨터에 이미 깔린 것이다. 깔린 것이 하나뿐이면 묻지 않고 그것으로 정한다. 깔려 있지 않은 것을 사람이 말하면 설치 명령을 보여 주고 사람이 직접 설치하게 한다. 컴퓨터 전체에 쓰이는 도구는 이 스킬이 설치하지 않는다. 기존 프로젝트가 쓰는 패키지 매니저가 깔려 있지 않으면 "멈출 때" 템플릿으로 끝낸다.
- "없음"은 "패키지 매니저"의 선택지에는 넣지 않는다. "프레임워크"의 "없음"은 위 규칙을 따른다. "테스트 도구", "스타일", "미리 볼 자리"에서 고르면 되묻지 않고 아래 한 줄로 알린 뒤 다음 항목으로 넘어간다.

  ```
  <항목> 없이 진행합니다. "<조건>" 조건을 건너뛰고, <못 하게 되는 일>.
  ```

- "컴포넌트 자리와 데이터 자리"는 한 질문으로 묻는다. 선택지 대신 추천 폴더 이름을 보여 주고, 그대로 쓸지 다른 이름을 쓸지 답하게 한다.
- 사용자가 남은 항목을 추천대로 하자고 하면 더 묻지 않고 추천값으로 채운다.
- 기존 프로젝트가 쓰는 도구는 바꾸자고 하지 않는다.

항목이 모두 정해지면 "고른 것" 화면으로 확정받는다.

```
셋업 · 고른 것

- 앱 이름: <이름>
- 위치: <지금 폴더 | 하위 폴더 경로>
- 만드는 것: <웹 앱 | 모바일 앱 | …>
- 프레임워크: <프레임워크>
- 패키지 매니저: <패키지 매니저>
- 테스트 도구: <테스트 도구>
- 스타일: <스타일 방식>
- 컴포넌트 자리: <폴더> · 데이터 자리: <폴더>
- 미리 볼 자리: <방식>
확인 안 된 조합: <항목>, <항목>

이대로 진행할까요? 번호로 답해 주세요.
1. 이대로 진행
2. 취소

바꾸고 싶은 항목이 있으면 말씀해 주세요.
```

- "위치"와 "만드는 것"은 새 프로젝트일 때만 쓴다. "확인 안 된 조합"은 스택 파일에 없는 항목이 있을 때만 쓴다.
- "스타일", "컴포넌트 자리 · 데이터 자리", "미리 볼 자리"는 화면이 있는 프로젝트일 때만 쓴다.
- 값 옆에 출처를 나타내는 말("추천", "요청에서", "찾음")은 붙이지 않는다.
- 사용자가 바꿀 항목을 말하면 반영해 화면을 다시 보여 준다. 바뀐 값이 나머지 항목과 함께 쓸 수 있는지 위와 같은 방법으로 다시 확인한다.
- "취소"를 고르면 "취소했을 때" 템플릿으로 끝낸다.

### 3. 조건 대조

고른 것을 기준으로 조건마다 상태를 정한다. 여기까지도 읽기만 한다.

- 설정 파일과 명령을 읽어 판단한다. 조건의 뜻을 채우는지를 본다. 도구가 깔려 있기만 하고 조건을 채우지 못하면(예: 린터는 있는데 커밋 전에 돌지 않음) ✅가 아니다.
- 기존 설정이 조건과 다른 방향이면(규칙이 꺼져 있음, 커밋 전 훅이 다른 일을 함) ⚠️다. 프로젝트가 이미 쓰는 도구가 스택 파일의 추천과 다른 것은 충돌이 아니다.
- 스택 파일에 없는 도구는 조건마다 그 도구로 채울 방법을 공식 문서에서 찾는다.
  - 프로젝트가 이미 쓰는 도구로 채울 방법을 찾지 못한 조건은 ⏭로 두고 설명에 `<도구>로 채울 방법을 찾지 못함`이라고 쓴다.
  - 뼈대가 기본으로 주는 도구로 채울 방법을 찾지 못하면 스택 파일의 추천 도구를 쓴다.
- 새 프로젝트는 뼈대를 만든 뒤의 상태로 적는다. 뼈대가 채워 주는 조건도 ➕로 적고 설명에 "뼈대가 만듦"이라고 쓴다.
- 프로젝트 폴더 밖에 내려받는 것이 있는 조건은(예: 화면을 찍을 브라우저) 설명에 그것을 적는다.

"할 일" 화면을 보여 준다.

```
셋업 · 할 일 (<앱 이름>)

✅ 충족 · ➕ 추가 · ⚠️ 충돌 · ⏭ 건너뜀
조건 <전체>개 · ✅ <개수> · ➕ <개수> · ⚠️ <개수> · ⏭ <개수>

Project
- <이모지> <조건> → <할 일이나 지금 상태>

UI
- <이모지> <조건> → <할 일이나 지금 상태>

AI
- <이모지> <조건> → <할 일이나 지금 상태>

Recommended
- <이모지> <조건> → <할 일이나 지금 상태>

뼈대: <뼈대를 만드는 명령>
확인 안 된 조합: <도구>, <도구>
충돌 (<개수>)
<번호>) <조건>: <지금 상태>
   추천: 그대로 두고 이 조건은 건너뜀 / 다른 선택: <바꾸는 방법>

어떻게 진행할까요? 번호로 답해 주세요.
1. 모두 추천대로 진행
2. 충돌을 하나씩 고르며 진행
3. 취소
```

- 조건 수를 세는 줄에서 0개인 상태는 뺀다. ✅인 조건은 `→` 없이 조건 이름만 쓴다.
- "뼈대"는 새 프로젝트일 때만, "충돌"은 ⚠️가 있을 때만 쓴다. "확인 안 된 조합"은 "고른 것" 화면에 나오지 않은, 스택 파일에 없는 도구가 있을 때만 쓴다.
- 충돌의 추천은 언제나 "그대로 두고 이 조건은 건너뜀"이다. 그래서 "모두 추천대로 진행"은 기존 설정을 바꾸지 않는다.
- ⏭의 설명에는 이유를 쓴다. 예: `고르지 않음`, `"정적 검사"를 건너뛰어 함께 건너뜀`
- ⚠️가 없으면 선택지를 아래로 바꾼다.

  ```
  진행할까요? 번호로 답해 주세요.
  1. 진행
  2. 취소
  ```

- ➕와 ⚠️가 모두 없으면(다시 불렀고 더할 것이 없을 때) 선택지를 아래로 바꾼다. "조건 확인만 다시 하기"를 고르면 4번을 건너뛰고 5번으로 간다.

  ```
  추가할 것이 없습니다. 번호로 답해 주세요.
  1. 조건 확인만 다시 하기
  2. 끝내기
  ```

- "충돌을 하나씩 고르며 진행"을 고르면 충돌마다 두 선택을 번호로 묻고, 다 고르면 설치로 넘어간다. 바꾸기로 한 조건은 ➕로, 두기로 한 조건은 ⏭로 다룬다.
- "취소"나 "끝내기"를 고르면 "취소했을 때" 템플릿으로 끝낸다.

### 4. 설치

"할 일" 화면에서 진행을 고른 뒤에만 한다.

- 새 프로젝트면 뼈대를 먼저 만든다. 프레임워크가 "없음"이면 언어 파일의 "뼈대"를 따른다. 뼈대 도구가 커밋을 만들거나 기존 파일을 지우지 않게 한다. 뼈대를 만들지 못하면 "멈출 때" 템플릿으로 끝낸다.
- ➕인 조건만 다룬다. 스택 파일의 "꼭 지켜야 하는 것"을 모두 채운다.
- 조건을 채우는 것 말고도, 이번에 더하는 도구가 잘 돌아가게 하는 것을 함께 더할 수 있다. 그 도구의 공식 문서가 함께 쓰라고 안내하는 것, 고른 도구끼리 맞물리게 하는 것, 만든 자리를 바로 써 볼 예시까지다. 고른 것과 상관없는 도구는 넣지 않는다. 더한 것은 보고의 "함께 더한 것"에 적는다.
- 기존 설정 파일은 필요한 부분만 더한다. 파일을 통째로 바꾸지 않는다.
- 설치 명령이 실패하면 그 조건은 ❌로 두고 다음 조건으로 넘어간다. 같은 명령을 옵션만 바꿔 되풀이하지 않는다.
- 커밋하지 않는다.

AI 조건은 스택과 상관없이 프로젝트의 `.claude/settings.json`에 둔다. 파일이 이미 있으면 아래 배열에 항목만 더한다.

**검사 건너뛰기 금지**: 훅 스크립트 `${CLAUDE_SKILL_DIR}/assets/block-hook-bypass.mjs`를 고치지 않고 그대로 `.claude/hooks/`에 복사하고, 아래처럼 등록한다.

```json
{
  "hooks": {
    "PreToolUse": [
      {
        "matcher": "Bash",
        "hooks": [
          {
            "type": "command",
            "command": "node \"$CLAUDE_PROJECT_DIR/.claude/hooks/block-hook-bypass.mjs\""
          }
        ]
      }
    ]
  }
}
```

- `if` 필드로 `git` 명령만 걸러내지 않는다. 환경 변수를 앞에 붙인 커밋처럼 `git`으로 시작하지 않는 명령이 빠진다. 판정은 스크립트가 한다.
- 스크립트는 `git commit`의 `--no-verify`와 `-n`을 막는다. 훅 도구마다 따로 있는 건너뛰는 방법은 스택 파일이 다룬다.

**검사 설정 보호**: `permissions.ask`에 보호할 파일마다 규칙을 하나씩 넣는다. `/`로 시작하는 경로는 프로젝트 루트 기준이다.

```json
{
  "permissions": {
    "ask": ["Edit(/<검사 설정 파일>)", "Edit(/.claude/settings.json)", "Edit(/.claude/hooks/**)"]
  }
}
```

- 보호할 파일은 커밋 전 검사가 돌리는 검사들의 설정 파일과, 커밋 전 검사 자체의 설정 파일과 훅 폴더다. `.claude/`의 두 줄은 언제나 넣는다. 스택 파일이 빼라고 한 파일은 넣지 않는다.
- 아직 없는 설정 파일의 이름도 넣는다. 새로 만들어 검사를 바꾸는 것도 막아야 한다.
- 이 규칙은 4번에서 넣지 않는다. 5번에서 다른 조건의 확인을 모두 끝낸 뒤에 넣는다. 먼저 넣으면 이 스킬이 설정 파일을 만들거나 확인 중에 고칠 때마다 확인 창이 뜬다.

### 5. 확인

➕로 설치한 조건과 ✅였던 조건을 모두 확인한다. ⏭인 조건은 확인하지 않는다.

**검사로 막는 조건** (정적 검사, 타입 검사 엄격, 테스트 도구, 커밋 전 검사, 컴포넌트의 서버 호출·저장 금지, 컴포넌트와 데이터의 분리, 접근성)

1. 스택 파일이 정한 것을 담은 위반 예시를 써서 프로젝트에 넣고 stage한다.
2. 커밋을 만들지 않고 `git hook run pre-commit`으로 커밋 전 검사를 돌린다. 실패하고(종료 코드가 0이 아님), 출력에 그 조건의 규칙이 나와야 한다.
3. 통과 예시로 바꿔 다시 돌린다. 통과해야 한다.
4. `git rm --cached -q -f <예시 파일>`로 stage에서 빼고 파일을 지운다. 커밋이 하나도 없는 저장소에서도 되는 명령이다.

- 시작하기 전에 `git diff --cached --name-only`가 비어 있어야 한다. 사람이 stage해 둔 변경이 있으면 커밋 전 검사가 그 파일까지 고친다. 비어 있지 않으면 커밋 전 검사를 거치는 확인을 하지 않고, 해당 조건을 "확인 못 함"(이유: `stage된 변경이 있음`)으로 보고한다.
- `git hook run`은 git이 설정된 훅 경로로 훅을 부른다. 그래서 훅이 커밋에 걸려 있는지도 함께 확인된다. 이 명령이 없는 git(2.36 미만)에서는 훅 파일을 직접 실행하고 훅 경로 설정을 따로 본다.
- 조건 하나씩 따로 본다. 여러 위반을 한 번에 넣으면 어느 규칙이 막았는지 알 수 없다.
- 예시 파일은 그 검사가 실제로 보는 폴더 안에 둔다. 검사가 보지 않는 자리에 두면 막지 못한 것처럼 보인다.
- "정적 검사"의 위반 예시는 지금 적용된 설정에서 error인 규칙을 어기게 쓴다. 경고인 규칙은 어겨도 커밋 전 검사가 통과한다.
- 예시 파일의 이름에 `__harness_check__`를 넣는다. 남은 것을 찾기 쉽다.
- "커밋 전 검사"는 따로 예시를 넣지 않는다. 다른 조건의 예시가 커밋 전 검사를 거쳐 실패하고 통과했으면 충족이다.
- 통과 예시를 돌릴 때 걸린 시간을 한 번 잰다.
- 기존 코드가 검사에 걸리면 예시의 결과와 구분해서 본다. 기존 코드의 위반은 개수만 세어 보고한다.

**고쳐지는 조건** (코드 모양 통일)

- 모양이 흐트러진 예시를 stage하고 커밋 전 검사를 돌린다. 통과하고, stage된 내용이 포매터가 고친 모양이어야 한다.

**있는지 보는 조건** (git 저장소, 명령 이름, 컴포넌트 자리와 데이터 자리, 미리 볼 자리, 화면 찍기)

- 명령은 실제로 돌려 본다. "화면 찍기"는 미리 볼 자리를 띄워 한 장 찍고 파일이 생겼는지 본다. 찍은 이미지를 읽지는 않는다. 찍은 파일은 지운다.

**권고** (토큰만 쓰기)

- 위반 예시에 경고가 뜨는지만 본다. 경고는 검사 도구를 직접 돌려서 본다. 커밋 전 검사는 성공한 검사의 출력을 숨길 수 있다. 커밋 전 검사는 통과해야 한다.

**AI 조건**

- 검사 건너뛰기 금지: `git commit --dry-run --no-verify`를 실제로 시도한다. `--dry-run`이라 막히지 않아도 커밋이 생기지 않는다. 도구 호출이 막히고 훅의 메시지가 돌아오면 충족이고, git의 출력이 보이면 막지 못한 것이다. 스택 파일이 정한 건너뛰는 방법도 같은 식으로 시도한다.
- 앱을 하위 폴더에 만들었으면 AI 조건은 이 대화에서 확인할 수 없다. "확인 못 함"으로 보고한다.
- 검사 설정 보호: 5번의 맨 마지막에 한다. 다른 조건의 확인과 아래 `git status` 확인을 모두 끝내고, ➕였으면 권한 규칙을 넣은 뒤다.
  1. 보호 대상 파일 하나를 고른다. `.claude/` 안의 파일과 훅 폴더의 파일은 고르지 않는다. Claude Code가 권한 규칙 없이도 따로 지키는 자리라, 규칙이 동작하는지 알 수 없다.
  2. 아래 한 줄로 알린다.

     ```
     검사 설정 보호를 확인합니다. <파일>을 고쳐도 되는지 묻는 창이 뜨면 허용해 주세요. 파일 내용은 바뀌지 않습니다.
     ```

  3. 그 파일을 Write 도구로 지금 내용 그대로 다시 쓴다. Bash로 쓰면 확인 창이 뜨지 않는다. 이 호출은 다른 도구 호출과 함께 보내지 않는다.
  4. 거절로 돌아오면 충족이다. 거절하면 대화가 멈추므로, 사람의 다음 말에 6번 보고로 이어 간다.
  5. 성공으로 돌아오면 아래 질문으로 묻는다. 허용한 것과 창이 뜨지 않은 것은 결과가 같아서 사람만 안다. "떴음"이면 충족이고 "안 떴음"이면 ❌다.

     ```
     <파일>을 고쳐도 되는지 묻는 창이 떴나요? 번호로 답해 주세요.
     1. 떴음
     2. 안 떴음
     ```

확인이 실패하면 설정을 한 번 고쳐 다시 확인한다. 그래도 실패하면 ❌로 보고한다. 규칙을 끄거나 약하게 해서 통과시키지 않는다.

확인이 끝나면 `git status`로 예시 파일이 남지 않았는지 본다.

### 6. 보고

```
셋업 완료 · <앱 이름>

조건 <전체>개 · ✅ <개수> · ⏭ <개수> · ❌ <개수>
- ❌ <조건> → <막지 못한 이유>
- ⏭ <조건> → <건너뛴 이유>
확인 못 함: <조건>, <조건> (<이유>)
기존 코드의 위반: <검사> <개수>건 (고치지 않음)
확인 안 된 조합: <항목>, <항목>
함께 더한 것
- <더한 것> → <더한 이유>
커밋 전 검사 시간: 약 <초>초
바뀐 파일: <개수>개 (커밋하지 않음)
다음: <읽는 쪽이 할 행동>
```

- 0개인 상태는 조건 수를 세는 줄에서 뺀다. ✅인 조건은 줄로 쓰지 않는다.
- "확인 못 함", "기존 코드의 위반", "확인 안 된 조합", "함께 더한 것"은 있을 때만 쓴다. "커밋 전 검사 시간"은 "커밋 전 검사"가 ✅일 때만 쓴다.
- "함께 더한 것"은 4번에서 조건을 채우는 것 말고 더한 것이다. 보고 뒤에 사람이 빼 달라고 하면, 그것과 그것 때문에 더한 설정을 빼고 걸리는 조건을 다시 확인한다.
- 4번을 건너뛰고 확인만 했으면 첫 줄을 `셋업 확인 · <앱 이름>`으로 쓰고 "바뀐 파일" 줄을 뺀다.
- `다음:` 줄은 위에서부터 처음 해당하는 것을 쓴다.
  - 하위 폴더에 만들었으면: `<폴더>에서 Claude Code를 다시 열고 셋업을 다시 요청`
  - ❌가 있으면: `❌ 조건의 원인을 확인한 뒤 셋업을 다시 요청`
  - 그 밖에는: `바뀐 파일을 확인한 뒤 커밋`

#### 취소했을 때

```
셋업 취소 · 아무것도 바꾸지 않음
```

#### 멈출 때

```
셋업 중단 · <이유 한 줄>
바뀐 파일: <개수>개 (커밋하지 않음)
다음: <읽는 쪽이 할 행동>
```

- 이 스킬이 할 수 없는 일을 사람이 먼저 해야 해서 더 나아갈 수 없을 때 쓴다. 예: 프로젝트가 쓰는 패키지 매니저나 실행 환경이 이 컴퓨터에 없음, 뼈대를 만들지 못함
- 조건 하나를 채우지 못하는 것은 멈출 일이 아니다. 그 조건만 ⏭나 ❌로 두고 계속한다.
- "바뀐 파일"은 4번에서 바꾼 것이 있을 때만 쓴다.
- `다음:` 줄에는 사람이 그대로 쓸 수 있는 명령이 있으면 넣고, 셋업을 다시 요청하라는 말로 끝낸다.
