# Decision Resolver

commit-writer가 떼어낸 결정 대기 변경의 결정을 사람에게서 받아 기록하고, 결정 대기 상태를 끝내는 스킬이다. git 작업과 기록만 한다. 결정을 코드에 반영하는 일은 부른 쪽(사람이나 AI)이 한다.

## 핵심 원칙

- **답은 사람이 정한다.** 추천을 고르거나 답을 지어내지 않는다. 사람이 "추천대로"를 골랐을 때만 추천을 고른 것으로 본다.
- **두 단계로 나눈다.** 1단계는 답을 모아 결정을 확정한다. 부른 쪽이 반영하고 커밋, push한 뒤, 2단계에서 보고서와 제목을 고쳐 마무리한다.
- **하나씩 묻는다.** 브랜치가 여럿이면 개요를 먼저 보여주고 브랜치마다 진행한다. 한 브랜치 안에서는 1단계 → 2단계 순서로, 질문 하나에 한 단계만 담는다.
- **브랜치를 옮기지 않는다.** 모든 작업을 지금 브랜치에서 한다. 다른 브랜치의 내용은 원격 브랜치(`origin/<브랜치>`)로 읽는다.
- **원격을 바꾸는 일은 좁게 한다.** 결정 기록, 보고서 코멘트의 결정 부분, PR 제목, Draft 해제, 아래 PR이 머지된 쌓인 PR의 base 변경만 한다.
- **잘못된 base로는 Draft를 풀지 않는다.** PR의 base가 열린 PR의 작업 브랜치면 Draft를 유지한다. GitHub은 Draft PR의 머지를 막으므로, 아래 PR보다 먼저 머지되거나 아래 브랜치로 잘못 들어가는 일이 생기지 않는다.
- **맞는 규칙이 없으면 처리하지 않는다.** 그 브랜치의 기록과 PR을 바꾸지 않고, 본 상태를 그대로 알린다.

|---|---|---|

| `${CLAUDE_PLUGIN_ROOT}/shared/report.md` | PR이 있는 브랜치가 하나라도 있을 때, 답을 모으기 전에 | 보고서의 결정 부분(표시 안쪽)을 읽고 고친다 |
| `${CLAUDE_PLUGIN_ROOT}/shared/commit-types.md` | 결정 대기가 끝나 제목을 바꾸기 직전에 | 제목의 🚧를 type 이모지로 되돌린다 |

| `references/branch-states.md` | 정상 상태가 아닌 브랜치가 있을 때 | 브랜치 상태별 처리 |

## 안내 언어와 형식

- 안내와 보고서 내용은 한국어 개조식으로 쓴다. 섹션 제목은 영어로 쓴다.
- 서명 줄을 붙이지 않는다.

안내와 보고서는 이 문서와 공통 파일의 템플릿을 그대로 따른다.

- `<…>` 자리만 채운다. 라벨, 기호, 줄 순서는 바꾸지 않는다.
- "있을 때만" 줄은 해당할 때만 쓰고, 없으면 통째로 뺀다.
- 굵게(`**`) 같은 꾸밈이나 템플릿에 없는 줄을 더하지 않는다.
- 안내는 템플릿 자체가 응답 전체다. 응답의 첫 줄은 템플릿의 첫 줄이다. 앞뒤에 문장을 덧붙이지 않는다. "남은 일 이어 하기"로 이어 하는 일의 글은 안내 뒤에 붙일 수 있다.
- 템플릿 바깥을 코드 블록(```)으로 감싸지 않는다.
- 브랜치 이름, 해시, PR 번호는 git과 gh가 출력한 값을 그대로 옮긴다.
- `다음:` 줄은 스킬이 끝난 뒤 읽는 쪽이 할 행동이다. 질문이 아니며, 스킬은 답을 기다리지 않는다. 행동은 "~ 후 다시 요청", "<스킬>로 ~"처럼 동작으로 쓴다. 조건에 따라 갈리면 조건을 앞에 짧게 쓴다.
- 결정 줄의 라벨은 PR 보고서와 같게 쓴다(미결정 이유, 현재 임시값, 의존, 관련 위치). 체크박스와 링크는 빼고, 관련 위치는 `<경로>:<줄>`만 쓴다.
- 진행 선택지는 번호로, 결정의 선택지는 번호 없이 이름으로 쓴다. 둘이 섞이지 않게 하기 위해서다.

## 모드

| 모드 | 호출 | 동작 |
|---|---|---|
| 확인 (기본) | `/git-kit:decision-resolver` 또는 "결정했어" | 브랜치마다 확인받고 확정하거나 마무리한다 |
| 자동 | `/git-kit:decision-resolver --auto` | 묻지 않고 확정과 마무리를 한다. 사람의 답이 없는 결정은 남은 결정으로 돌려준다 |

- 인자에 `--auto`가 그대로 있을 때만 자동 모드다. 그 밖의 모든 경우는 확인 모드다. 누가 호출했는지로 모드를 추측하지 않는다.
- 자동 모드는 추천을 고르지 않고, Draft를 해제하지 않는다. base 변경은 한다. 아래 PR이 이미 머지됐을 때만 하는 정해진 동작이고, Draft는 그대로라 머지로 이어지지 않기 때문이다.

## 남은 일 이어 하기

이 스킬이 끝난 뒤에도 할 일이 남았을 때의 규칙이다. 마무리 안내는 템플릿대로 쓰고, 이어서 하는 일의 글은 안내 뒤에 따로 쓴다.

- **남은 일**: 지금 요청에 사람이 직접 말한 일과, 이 스킬을 부른 쪽(AI)이 하던 작업의 나머지다. 안내의 `다음:` 줄에 적힌 일과 예전 대화에 나온 일은 남은 일이 아니다.
- **이어 할 때**: 스킬이 끝나면 남은 일을 이어서 한다. 자동 모드도 같다.
  - 확인 질문에서는 지금처럼 멈추고, 답을 받아 스킬이 끝난 뒤 이어 한다.
  - 남은 일을 맡는 git-kit 스킬이 있으면 그 스킬을 부른다. 그 스킬의 확인 질문은 그대로 한다.
- **하지 않을 때**: 스킬이 실패나 취소로 끝나면 남은 일을 하지 않고 마무리 안내로 끝낸다.
- 이 스킬보다 먼저 해야 하는 일(예: 테스트가 통과하면 커밋)은 남은 일이 아니다. 요청한 순서대로 한다.

## 하지 않는 일

머지, rebase, force push, push, 브랜치 이동, 브랜치 삭제, PR 닫기, PR base 바꾸기(`references/branch-states.md` 18, 20번만 예외), PR 만들기, 코드 수정, 답 정하기. 필요하면 안내의 `다음:` 줄로 알린다.

## 진행 순서

- [ ] 1. 준비
- [ ] 2. 답 모으기
- [ ] 3. 할 일 정하기
- [ ] 4. 1단계: 결정 확정
- [ ] 5. 2단계: 결정 마무리
- [ ] 6. 완료 안내

### 1. 준비

1. `decision-record.md`를 읽는다.
2. **GitHub 연결 확인**: gh(`gh auth status` 성공)와 GitHub MCP 중 하나가 있어야 한다. 둘 다 없으면 기록과 PR을 바꾸지 않고 아래로 알린 뒤 끝낸다. PR이 있는지 알 수 없어 PR 없는 브랜치로 잘못 처리할 수 있기 때문이다.
   ```
   결정 처리 못함 · GitHub 연결 없음
   해결: gh 설치(https://cli.github.com) 후 `gh auth login`, 또는 GitHub MCP 연결
   ```
3. `git fetch --prune` 을 한 번 한다.
4. **범위**: 아래 순서로 정한다.
   - 사용자가 "결정사항들", "전부"처럼 전체를 말했으면 → 모든 결정 대기 브랜치
   - 지금 브랜치에 기록(`refs/git-kit/decisions/<브랜치>`)이 있거나, 지금 브랜치 PR의 제목이 🚧로 시작하면 → 지금 브랜치만
   - 그 밖 → 모든 결정 대기 브랜치
   - 모든 결정 대기 브랜치는 `git for-each-ref refs/git-kit/decisions/`의 브랜치와, 열린 PR 중 제목이 🚧로 시작하는 브랜치를 합친 것이다.
   - 여기에 아래 PR 머지를 기다리는 브랜치를 더한다. 열린 Draft PR(`gh pr list --draft --state open`) 중 보고서 결정 부분의 `Draft 유지:` 줄이 `아래 PR 머지 대기`인 브랜치다. 결정 부분은 `report.md`의 표시로 찾으므로, 열린 Draft PR이 있으면 이때 `report.md`를 읽는다. 결정은 끝났고 base 변경과 Draft 해제만 남은 경우라 `references/branch-states.md` 20번으로 처리한다.
5. **PR 조회**: 브랜치마다 PR을 한 번 읽는다. `gh pr view <브랜치> --json number,state,isDraft,title,baseRefName,url`
6. **상태 판단**: 브랜치마다 아래를 모두 만족하면 정상이다. 하나라도 아니거나 확실하지 않으면 `references/branch-states.md`를 읽고 그대로 처리한다.
   - 결정 기록이 있고 새 형식으로 읽힌다.
   - PR이 열려 있고 제목이 🚧로 시작하며 Draft다. 또는 PR이 없다.
   - 로컬 브랜치와 원격 브랜치가 같다. 또는 원격 브랜치가 없다.
   - PR의 base가 어떤 PR의 작업 브랜치도 아니다. 또는 PR이 없다.
7. **순서**: PR이 있는 브랜치를 PR 번호순으로, 쌓인 PR은 아래 PR을 먼저 둔다. PR이 없는 브랜치는 그 뒤에 브랜치 이름순으로 둔다.
8. **기준 커밋**: 원격 브랜치가 있으면 `origin/<브랜치>`, 없으면(push 전) 로컬 브랜치를 기준으로 결정 시점과 반영 커밋을 본다.
9. **보고서 형식**: 처리할 브랜치 중 PR이 있는 브랜치가 하나라도 있으면 `report.md`를 읽는다. 답을 모을 때 보고서의 결정 표시를 알아야 하기 때문이다.

### 2. 답 모으기

`references/answers.md`를 읽고, 브랜치마다 그대로 답을 모은다.

- 출처: PR 보고서 체크박스, PR 코멘트, 대화
- D마다 결과를 하나로 정한다: 답 있음, 답 충돌, 체크 여러 개, 사람 확인 필요, 대기
- 결정 의존을 번호 순서대로 판단한다.

### 3. 할 일 정하기

브랜치마다 할 단계를 정한다. 둘 다 할 수 있다.

- 1단계(결정 확정): 새로 확정할 답(대기였던 D에 답이 생김, 결정된 답이 바뀜)이나 대기인 D가 있을 때
- 2단계(결정 마무리): 결정됨인 D에 반영 커밋 후보가 있을 때. 또는 아래 PR 머지를 기다리던 PR에서 아래 PR이 머지됐을 때(`references/branch-states.md` 20번)
- 둘 다 없으면 할 일 없음(반영 기다림, 아래 PR 머지 기다림)이다.

브랜치마다 1단계 → 2단계 순서로, 해당하는 단계만 묻는다. 1단계에서 확정한 D는 아직 반영 전이므로, 1단계를 먼저 해야 2단계에서 결정 대기가 끝인지 계속인지 정확히 안다.

#### 개요 (할 일이 있는 브랜치가 2개 이상일 때만)

```
결정 처리 준비 · 브랜치 <브랜치 수>개

- <브랜치> · PR #<번호>: 확정할 답 <개수>개, 대기 <개수>개, 반영 <개수>개
- <브랜치> · PR #<번호>: 반영 기다림
- <브랜치> · PR #<번호>: [처리하지 않음] <상태>

어떻게 진행할까요? 번호로 답해 주세요.
1. 순서대로 하나씩 처리 (<할 일이 있는 브랜치 수>개 브랜치)
2. 브랜치 골라 처리
3. 취소
```

- 브랜치 목록은 진행 선택지와 섞이지 않게 `-`로 쓴다.
- "확정할 답", "대기", "반영"은 0개면 그 부분을 뺀다.
- `· PR #<번호>`는 PR이 있을 때만 쓴다.
- 할 일이 있는 브랜치가 1개면 개요 없이 바로 그 브랜치의 단계를 보여준다.
- 자동 모드는 개요와 질문 없이 모든 브랜치를 처리한 뒤 완료 안내만 쓴다.

#### 선택지 공통 규칙

- 브랜치 템플릿의 `(<순서>/<전체>)`는 할 일이 있는 브랜치가 2개 이상일 때만 쓴다.
- 브랜치가 2개 이상이면 마지막 두 선택지는 `이 브랜치 건너뛰기`, `그만하기`다. 1개면 `취소` 하나다.
- `이 브랜치 건너뛰기`는 그 브랜치의 남은 단계를 모두 건너뛴다. `그만하기`와 `취소`는 남은 단계와 브랜치를 모두 멈추고 완료 안내를 쓴다.
- 선택지를 빼면 번호를 다시 매긴다.
- 선택지 목록과 마지막 안내 줄 사이에는 빈 줄을 둔다. 빈 줄이 없으면 마크다운에서 안내 줄이 마지막 선택지에 붙어 보이기 때문이다.

### 4. 1단계: 결정 확정

```
결정 확정 준비 · <브랜치> · PR #<번호> (<순서>/<전체>)

- D<번호>. <결정할 것>: <고른 답> (<답한 곳>)
  - 관련 위치: <경로>:<줄>
  - 현재 임시값: <임시값>
  - 무시한 답: @<사람>
- D<번호>. <결정할 것>: 필요 없음 (D<번호>가 <답>)
- D<번호>. <결정할 것>: [대기]
  - 미결정 이유: <이유>
  - 의존: D<번호>가 <선택지>일 때만 필요
  - 현재 임시값: <임시값>
  - <선택지> (추천): <장단점>
  - <선택지>: <장단점>
- D<번호>. <결정할 것>: [대기] 선택지 없음
  - 미결정 이유: <이유>
- D<번호>. <결정할 것>: [<남은 이유>] <내용>

어떻게 진행할까요? 번호로 답해 주세요.
1. 위 답으로 확정, 대기는 추천대로
2. 위 답으로 확정, 대기는 나중에
3. 이 브랜치 건너뛰기
4. 그만하기

다른 답을 고르려면 "<예시 답>"처럼 말씀해 주세요.
선택지가 없는 D<번호>의 답을 말씀해 주세요.
D<번호>의 답을 하나 골라 말씀해 주세요.
```

- D마다 한 번 쓴다. 이미 반영됐거나 이번 2단계에서 마무리할 D는 쓰지 않는다. 결정됐지만 아직 반영 안 된 D는 다시 보여준다.
- `(<답한 곳>)`은 체크박스가 아닐 때만 붙인다. 예: `(대화)`, `(대화, 추천 따름)`, `(PR 코멘트 @사람, 자유 답 "<원문>")`
- 이미 결정된 답이 바뀌었으면 `<고른 답>` 뒤에 ` (이전: <이전 답>)`을 붙인다. 답한 곳이 있으면 그 괄호 안에 함께 쓴다. 예: `30분 뒤 자동 해제 (대화, 이전: 메일 링크)`
- 관련 위치는 지금 코드에서 다시 찾는다. 여러 곳이면 줄을 여러 개 쓴다. 현재 임시값, 의존, 무시한 답은 있을 때만 쓴다.
- 대기가 아닌 남은 이유는 `[의존 오류]`, `[답 충돌]`, `[체크 여러 개]`, `[사람 확인 필요]` 중 이 순서로 앞선 하나만 쓴다.

1, 2번 선택지와 마지막 줄은 상황에 따라 쓴다.

| 상황 | 1번 | 2번 | 마지막 줄 |
|---|---|---|---|
| 확정할 답 + 대기 | `위 답으로 확정, 대기는 추천대로` | `위 답으로 확정, 대기는 나중에` | 다른 답 고르기 |
| 확정할 답만 | `위 답으로 확정` | 없음 | `답을 더하거나 바꾸고 싶으면 말씀해 주세요.` |
| 대기만 | `추천대로 확정` | `나중에 답하기` | 다른 답 고르기 |
| 확정할 답 + 선택지 없는 대기만 | `위 답으로 확정, 대기는 나중에` | 없음 | 선택지 없는 D 줄만 |
| 선택지 없는 대기만 | `나중에 답하기` | 없음 | 선택지 없는 D 줄만 |

- 대기가 2개 이상이면 "추천대로"를 "모두 추천대로"로 쓴다.
- 선택지 없는 대기 D는 `[대기] 선택지 없음`으로 쓰고, 선택지 줄 대신 미결정 이유, 의존, 현재 임시값, 관련 위치 중 있는 것만 쓴다. 기록과 보고서에 선택지가 없을 때다(사람이 🚧 PR을 직접 만든 경우 등).
- "추천대로"와 "다른 답 고르기"는 선택지 있는 대기에만 해당한다. 선택지 없는 D는 "추천대로"를 골라도 대기로 남는다. 대기가 모두 선택지 없는 D면 위 표의 아래 두 줄을 쓴다.
- 선택지 없는 대기가 있으면 마지막 줄 아래에 `선택지가 없는 D<번호>의 답을 말씀해 주세요.`를 쓴다. 여럿이면 `D<번호>, D<번호>`로 잇는다. 선택지 없는 대기가 없으면 이 줄은 쓰지 않는다.
- 다른 답 고르기 줄: 대기가 1개면 `다른 답을 고르려면 "<선택지>"처럼 말씀해 주세요.`, 2개 이상이면 `다른 답을 고르려면 "D<번호> <선택지>"처럼 결정 번호와 함께 말씀해 주세요.` 예시는 첫 번째 대기 D의 추천이 아닌 선택지로 채운다.
- 남은 이유가 있는 D는 어느 선택지로도 확정하지 않는다.
  - 표의 상황을 고를 때만 선택지 없는 대기로 센다. 이때 선택지의 `대기는 나중에`는 `남은 것은 나중에`로 쓴다. 예: 확정할 답과 `[답 충돌]` D만 있으면 1번은 `위 답으로 확정, 남은 것은 나중에`다.
  - 남은 이유가 `[답 충돌]`이나 `[체크 여러 개]`인 D가 있으면 맨 아래에 `D<번호>의 답을 하나 골라 말씀해 주세요.`를 쓴다. 여럿이면 `D<번호>, D<번호>`로 잇는다. 없으면 이 줄은 쓰지 않는다.

대화로 답을 받았을 때:

- 선택지에 있는 답으로 남은 대기와 `[답 충돌]`, `[체크 여러 개]`인 D를 모두 답했으면, 그 답과 위 답을 함께 바로 확정한다. 답을 고른 것이 곧 결정이기 때문이다.
- 일부만 답했거나 선택지에 없는 답이 있으면, 답을 목록에 넣어 같은 템플릿을 다시 보여준다. 결정 의존도 다시 판단한다.

확정할 때:

1. 기록을 쓰기 직전에 PR을 다시 읽어 답을 비교한다. 바뀌었으면 그 브랜치는 건너뛰고 완료 안내에 `건너뜀: 확인 중 PR의 답이 바뀜`으로 알린다.
2. 기록의 D를 결정됨으로 바꾸고 `고른 답`, `답한 곳`, `결정한 때`, `결정 시점` 줄을 쓴다. 결정한 때는 지금 시각(`2026-11-06T14:30+09:00` 형식), 결정 시점은 기준 커밋의 짧은 해시다.
3. 필요 없음이 된 D는 상태만 바꾼다.
4. PR은 바꾸지 않는다. 단, 확정한 답이 PR 체크박스와 다르면(대화나 코멘트로 답했거나 답 충돌을 대화로 골랐을 때) 보고서 결정 부분의 그 D를 맞춘다. 체크를 확정한 답으로 바꾸고, 선택지에 없는 답이면 체크를 모두 푼다. 그리고 `report.md` 규칙대로 `- 결정:` 줄을 쓴다. 낡은 체크가 남으면 다음 실행에서 바뀐 답으로 읽히고, 자동 모드는 기록을 그 답으로 되돌리기 때문이다.
5. "나중에"를 골랐으면 대기 D는 그대로 둔다.
6. 그 브랜치에 2단계가 있으면 2단계로, 없으면 다음 브랜치로 넘어간다. 단계와 브랜치 사이에는 안내를 따로 쓰지 않는다.

자동 모드: 사람의 답이 있는 D만 확정한다. 대기와 사람 확인 필요는 확정하지 않고 "나중에"로 본다.

### 5. 2단계: 결정 마무리

**반영 커밋 찾기**: 결정 시점 이후 기준 커밋까지의 커밋 중 기록의 `관련 파일:`을 바꾼 커밋이다. 여러 개면 모두 쓴다. `관련 파일:` 줄이 없는 예전 기록이면 그 D의 관련 위치를 지금 코드에서 찾아 그 파일로 본다.

- 확인 모드: 후보를 보여주고 확인받는다. 틀렸으면 사람이 대화로 바로잡는다.
- 자동 모드: 관련 파일이 바뀐 경우만 반영됨으로 본다. 확실하지 않으면 결정됨으로 두고 남은 결정으로 돌려준다.
- 원격 브랜치가 있는데 로컬 브랜치가 앞서 있으면 그 브랜치는 2단계를 하지 않는다. 1단계는 한다. `references/branch-states.md` 13번을 따른다.

```
결정 마무리 준비 · <브랜치> · PR #<번호> (<순서>/<전체>)

- D<번호>. <결정할 것>: <고른 답> → 반영 커밋 <해시 7자리>
- D<번호>. <결정할 것>: 필요 없음
- D<번호>. <결정할 것>: <고른 답>
- D<번호>. <결정할 것>: [<남은 이유>]
- 결정 대기: <끝|계속>
- base: <지금 base> → <새 base> (#<아래 PR 번호> 머지됨)
- 머지 순서: #<번호> → #<번호> (이 PR)

어떻게 진행할까요? 번호로 답해 주세요.
1. 마무리하고 Draft 해제
2. 마무리만 (Draft 유지)
3. 이 브랜치 건너뛰기
4. 그만하기

반영 커밋을 바꾸고 싶으면 말씀해 주세요.
```

- 모든 D를 쓴다. 결정됐지만 반영 안 된 D는 고른 답만, 대기 등 남은 D는 남은 이유만 쓴다.
- 결정 대기 "끝"은 모든 D가 반영됨이나 필요 없음일 때다.
- `- base:` 줄은 base를 바꿀 때(`references/branch-states.md` 18, 20번)만 쓴다. 여러 단이 한 번에 풀리면 마지막 base까지 바꾼 결과를 쓴다.
- `- 머지 순서:` 줄은 base가 열린 PR의 작업 브랜치일 때만 쓴다. base를 바꿨으면 바꾼 뒤의 base로, 바꾸지 않았으면(`references/branch-states.md` 17번) 지금 base로 본다. 순서는 `report.md`의 "머지 순서"대로 만든다.
- 결정 대기가 계속되거나, PR이 없거나, `- 머지 순서:` 줄이 있으면 1, 2번 대신 `마무리` 하나를 쓴다. 머지 순서 줄이 있으면 아래 PR이 먼저 머지돼야 하므로 Draft를 풀지 않는다.

마무리할 때, 이 순서로 한다. 중간에 실패하면 그 브랜치를 멈추고 기록은 남긴다. 다시 실행하면 이어서 한다.

1. 쓰기 직전에 PR을 다시 읽어 답을 비교한다. 바뀌었으면 그 브랜치는 건너뛴다.
2. 기록의 D를 반영됨으로 바꾸고 반영 커밋을 쓴다.
3. base를 바꿀 때면 `gh pr edit <번호> --base <새 base>`로 바꾸고, 바뀐 base로 `references/branch-states.md`의 C표를 다시 본다.
4. PR이 있으면 보고서 코멘트의 결정 부분을 `report.md`대로 고친다. 결정 대기가 끝났으면 "결정이 모두 끝났을 때" 템플릿으로 바꾼다. 머지 순서 줄은 지금 base로 다시 계산한다. 예전 보고서면 `report.md`의 "예전 보고서"대로 함께 고친다.
5. 결정 대기가 끝났으면:
   - PR이 있고 제목이 🚧로 시작하면 `commit-types.md`를 읽고, 🚧를 그 type의 이모지로 바꾼다. `gh pr edit <번호> --title "<새 제목>"`
   - base가 열린 PR의 작업 브랜치면 Draft를 유지하고, 보고서의 `Draft 유지` 줄에 `아래 PR 머지 대기`를 쓴다. 아래 PR이 머지된 뒤 다시 실행하면 이 줄로 브랜치를 찾는다. 기록은 로컬에만 있지만 이 줄은 GitHub에 있어서, 다른 컴퓨터에서도 찾을 수 있다.
   - 그 밖에는 1번을 골랐으면 `gh pr ready <번호>`로 Draft를 해제한다. 2번을 골랐거나 자동 모드면 Draft를 유지하고, 보고서에 `Draft 유지` 줄을 쓴다.
   - 마지막에 기록을 지운다.
6. 결정 대기가 계속되면 제목, Draft, 기록 삭제는 하지 않는다.
7. 다음 브랜치로 넘어간다.

자동 모드: 묻지 않고 마무리한다. base 변경은 하고, Draft는 해제하지 않는다.

### 6. 완료 안내

모든 브랜치를 마치거나 "그만하기", "취소"를 고르면(두 모드 같음):

```
결정 처리 완료 · 브랜치 <처리한 브랜치 수>개

<브랜치> · PR #<번호>
- 확정: D<번호>, D<번호>
- 나중에: D<번호>
- 반영됨: D<번호>, D<번호>
- 결정 대기: <끝|계속>
- 제목: <새 제목>
- base: <이전 base> → <새 base> (#<아래 PR 번호> 머지됨)
- Draft: <해제됨|유지 (사람이 해제 필요)|유지 (아래 PR 머지 대기)>
- 머지 순서: #<번호> → #<번호> (이 PR)
- PR: 없음 (기록만 정리)
- 다음: PR 만들기(pr-writer). 결정이 세션을 넘어가므로 PR에 남김
- 다음: #<바로 아래 PR 번호> 머지 후 decision-resolver 다시 실행
- 다음: <브랜치 상태 안내>
- 건너뜀: <이유>

다음: 결정을 코드에 반영 → 커밋 → PR 갱신 → decision-resolver 다시 실행
```

- 처리하거나 건너뛴 브랜치만 쓴다. 각 줄은 해당할 때만 쓴다.
- "결정 대기", "제목", "base", "Draft", "PR: 없음"은 2단계를 했을 때만 쓴다. "제목"은 제목이 바뀌었을 때만, "Draft"는 PR이 있고 결정 대기가 끝났을 때만 쓴다.
- `- 다음: PR 만들기…` 줄은 PR이 없고 "나중에"인 D가 있을 때만 쓴다. 기록의 따온 브랜치가 기본 브랜치가 아니고 그 브랜치에도 PR이 없으면 `- 다음: 따온 브랜치 <따온 브랜치> PR 먼저, 그다음 이 브랜치 PR 만들기(pr-writer)`로 쓴다.
- "base"는 이번에 base를 바꿨을 때만 쓴다.
- "머지 순서"와 `- 다음: #<바로 아래 PR 번호> 머지 후 decision-resolver 다시 실행` 줄은 2단계를 해서 결정 대기가 끝났는데, PR의 base가 열린 PR의 작업 브랜치라 Draft를 유지했을 때만 쓴다. 1단계만 했거나 결정 대기가 계속되면 쓰지 않는다. 그때 남은 일은 코드 반영이라, 아래 PR 머지를 기다리라는 안내가 틀리기 때문이다.
- `- 다음: <브랜치 상태 안내>` 줄은 `references/branch-states.md`의 B표(11~13번)가 정한 문구를 그대로 쓴다.
- 마지막 `다음:` 줄은 이번에 확정한 D가 있을 때만 쓴다.
- 처리한 것이 없으면(모두 건너뜀) 첫 줄을 `결정 처리 안 함`으로 쓰고 브랜치 목록만 쓴다. 개요에서 취소했으면 `결정 처리 안 함 · 취소` 한 줄만 쓴다.
- 할 일이 있는 브랜치가 하나도 없으면 `결정 처리 안 함 · 할 일 없음` 다음에 개요와 같은 브랜치 목록을 쓴다.
