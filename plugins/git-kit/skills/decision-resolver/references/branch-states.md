# 브랜치 상태 판단

SKILL.md "1. 준비"의 상태 판단에서 읽는다. 브랜치마다 아래 표 A, B, C로 처리할지 정한다.

## 기본 규칙

- 아래 어떤 줄에도 맞지 않으면 그 브랜치는 처리하지 않는다. 기록과 PR을 바꾸지 않고, 본 상태를 `[처리하지 않음] <상태>`로 그대로 알린다.
- 자동 모드면 부른 쪽에 남은 결정으로 돌려준다.

## A. 결정 기록과 PR

| # | 기록 | PR | 처리 |
|---|---|---|---|
| 1 | 있음 | 열림, 🚧, Draft | 정상 처리 |
| 2 | 있음 | 열림, Draft 아님 또는 🚧 없음 | 정상 처리. 이미 된 마무리(Draft 해제, 제목)는 건너뛰고 완료 안내에 그대로 적는다 |
| 3 | 있음 | 닫힘 | 처리하지 않음. `[처리하지 않음] PR 닫힘` |
| 4 | 있음 | 머지됨 | 모든 D가 반영됨이나 필요 없음이면 기록만 지운다. 아니면 처리하지 않음. `[처리하지 않음] 결정 없이 머지됨` |
| 5 | 있음 | 없음 | 정상 처리. 답은 대화로만 받는다. PR 작업(보고서, 제목, Draft)은 건너뛴다 |
| 6 | 없음 | 열림, 🚧, Draft | 보고서의 결정 부분으로 기록을 다시 만든 뒤 정상 처리 (아래 "기록 다시 만들기") |
| 7 | 없음 | 일반 PR이거나 없음 | 대상 아님. 범위에 넣지 않는다. 단, 보고서의 `Draft 유지:`가 `아래 PR 머지 대기`인 열린 Draft PR은 20번을 따른다 |
| 8 | 예전 형식 | - | `decision-record.md`의 "예전 형식"대로 읽고 위 줄을 따른다 |
| 9 | 읽을 수 없음 | - | 기본 규칙. `[처리하지 않음] 기록을 읽을 수 없음` |

### 기록 다시 만들기 (6번)

다른 컴퓨터에서 만든 결정 대기 PR이라 로컬 기록이 없는 경우다.

- 확인 모드는 다시 만들기 전에 확인받는다. 브랜치 템플릿 대신 아래를 묻는다.
  ```
  기록 다시 만들기 · <브랜치> · PR #<번호>
  - 결정: D<번호>, D<번호> (보고서에서 읽음)

  어떻게 진행할까요? 번호로 답해 주세요.
  1. 기록 다시 만들고 계속
  2. 이 브랜치 건너뛰기
  3. 그만하기
  ```
- 결정할 것, 미결정 이유, 선택지, 의존은 보고서의 결정 부분에서 옮긴다. 따온 브랜치는 PR의 base, 기록한 날은 오늘이다.
- D의 상태와 답은 보고서의 `- 결정:` 줄로 정한다.
  - `- 결정:` 줄이 없음 → 대기
  - `- 결정: <고른 답>` → 결정됨
  - `- 결정: <고른 답> · 반영 커밋 [<해시>](<링크>)` → 반영됨. 링크 글자의 해시를 반영 커밋으로 옮긴다. 여러 개면 모두 옮긴다.
  - `- 결정: 필요 없음 (…)` → 필요 없음
  - `· 답한 곳: <곳>`이 있으면 답한 곳으로 옮기고, 없으면 PR 체크박스로 쓴다.
- 결정 시점은 지금의 기준 커밋으로 쓴다. 보고서에 없어서 원래 시점을 알 수 없기 때문이다. 결정한 때, 이전 답도 보고서에 없어 옮기지 않는다.
- 보고서의 결정 표시가 깨졌으면 다시 만들지 않는다. `report.md`의 "표시가 깨졌을 때"를 따른다.

## B. 로컬 브랜치와 원격

| # | 상태 | 처리 |
|---|---|---|
| 10 | 같음 | 정상 |
| 11 | 로컬 브랜치 없음 | 정상. 기준 커밋은 원격 브랜치. 완료 안내에 `- 다음: 반영하려면 브랜치 받기` 줄을 더한다 |
| 12 | 원격이 앞섬 | 정상. 기준 커밋은 원격 브랜치. 완료 안내에 `- 다음: 로컬 pull 필요` 줄을 더한다 |
| 13 | 로컬이 앞섬 | 1단계는 정상. 2단계는 하지 않는다. 완료 안내에 `- 다음: pr-writer로 push한 뒤 다시 실행` 줄을 더한다 |
| 14 | 갈라짐 | 기본 규칙. `[처리하지 않음] 로컬과 원격이 갈라짐` |
| 15 | 원격 브랜치 없음 (push 전) | 정상. 기준 커밋은 로컬 브랜치 |

- 비교는 `git rev-list --left-right --count <브랜치>...origin/<브랜치>`로 한다.
- 13번에서 1단계를 하는 이유: 확정은 원격 코드와 상관없이 할 수 있다. 반영 커밋 확인만 원격 기준이라 push가 필요하다.

## C. PR의 base

쌓인 PR(base가 다른 PR의 작업 브랜치인 PR)을 다룬다. 아래 PR의 브랜치를 지우지 않으면 GitHub이 base를 바꾸지 않아서, 그대로 머지하면 기본 브랜치가 아니라 아래 브랜치로 들어간다. 그래서 base가 열린 PR의 작업 브랜치인 동안은 Draft를 풀지 않고, 아래 PR이 머지되면 base를 바꾼다.

base 브랜치의 PR은 `gh pr list --head <base 브랜치> --state all --json number,state,baseRefName`으로 찾는다. 열린 PR이 있으면 그것을, 없으면 가장 최근에 머지된 PR을 본다.

| # | base 브랜치가 | 처리 |
|---|---|---|
| 16 | 어떤 PR의 작업 브랜치도 아님 (기본 브랜치, release 등) | 정상 |
| 17 | 열린 PR의 작업 브랜치 | 정상 처리. 2단계에서 결정 대기가 끝나도 Draft를 풀지 않는다 (`Draft 유지: 아래 PR 머지 대기`). 결정 부분의 머지 순서 줄은 `report.md`의 "머지 순서"대로 고친다 |
| 18 | 머지된 PR의 작업 브랜치 | 정상 처리. 2단계에서 base를 그 PR이 머지된 브랜치(그 PR의 `baseRefName`)로 바꾼 뒤 이 표로 다시 판단한다. 여러 단이면 16이나 17이 나올 때까지 되풀이한다. 확인 모드는 2단계 확인의 `- base:` 줄로 보여주고 함께 확인받는다 |
| 19 | 닫힌(머지 안 된) PR의 작업 브랜치 | 기본 규칙. `[처리하지 않음] 아래 PR #<번호> 닫힘` |
| 20 | 결정 기록 없음, 보고서의 `Draft 유지:`가 `아래 PR 머지 대기` | 결정은 이미 끝났다. 기록을 다시 만들지 않는다. base가 17이면 할 일 없음(아래 PR 머지 기다림). 18이면 2단계만 한다: base를 바꾸고, 결정 부분의 NOTE에서 머지 순서 줄과 `Draft 유지` 줄을 고치고, 16이 되면 확인 모드는 Draft 해제를 확인받는다. 기록 쓰기와 지우기는 건너뛴다 |

- 1단계(결정 확정)는 base와 상관없이 한다. Draft라서 base가 틀려도 머지되지 않는다.
- base를 바꾸는 건 2단계에서만 한다. 질문 하나에 한 단계만 담기 위해서다. 그 사이 머지 순서 줄이 낡을 수 있지만, Draft라서 해가 없고 2단계에서 다시 계산한다.
