# PR Writer

AI가 규칙대로 작업하며 git에 남긴 기록을 사람이 PR에서 검토할 수 있게 정리하는 스킬이다. PR 본문에는 무엇을 했는지를, PR 첫 코멘트의 보고서에는 AI가 판단한 것과 사람이 할 일을 담는다. 결정은 사람이 내리며, 이 스킬은 결정할 것을 정리해 보여줄 뿐 대신 정하지 않는다.

## 핵심 원칙

- **PR은 검토 관문이다.** 확인 모드에서는 원격 저장소(GitHub)를 바꾸는 작업(push, PR 생성과 갱신, 보고서 코멘트 작성)을 하기 전에 확인받는다. 자동 모드는 확인 없이 하되 PR을 Draft로만 만든다. Draft 해제(검토 요청)는 어느 모드에서도 이 스킬이 하지 않고 사람이 한다.
- **무엇과 왜를 나눈다.** 본문은 무엇을 했는지, 보고서 코멘트는 AI의 판단과 사람이 할 일을 담는다.
- **저장소 규칙이 이긴다.** 저장소의 PR 템플릿과 지침이 정한 형식과 요구를 따르고, 정하지 않은 부분만 이 스킬의 규칙으로 채운다.
- **확인한 것만 쓴다.** 근거 없이 단정하지 않는다. 확신이 없는 것은 Please check에 적는다.
- **PR 작성만 한다.** 커밋, 결정 반영, 코드 수정, 머지 후 정리는 하지 않는다.

## 안내 언어와 형식

- 사람이 읽는 설명(Summary, Decisions made, Please check 등의 내용)은 한국어 개조식("~함", "~노출")으로 쓴다.
- 제목, 섹션 제목, Changes 목록은 영어로 쓴다. 제목 형식은 "2. 제목과 본문"을 따른다.
- 확인 질문과 마무리 안내처럼 사용자에게 보여주는 글은 한국어로 쓴다.
- PR 본문과 코멘트에 `Generated with Claude Code` 같은 서명 줄을 붙이지 않는다. 서명을 붙이지 않았다는 사실은 안내에 따로 쓰지 않는다.

본문, 보고서 코멘트, 안내는 이 문서와 `references/`의 템플릿을 그대로 따른다.

- `<…>` 자리만 채운다. 라벨, 기호, 줄 순서는 바꾸지 않는다.
- "있을 때만" 줄과 섹션은 해당할 때만 쓰고, 없으면 통째로 뺀다.
- 굵게(`**`) 같은 꾸밈이나 템플릿에 없는 줄을 더하지 않는다.
- 템플릿 앞뒤에 문장(참고, 설명, 이유, 다음에 할 일)을 덧붙이지 않는다. 알릴 것은 템플릿의 줄로만 알린다.
- 안내는 템플릿 자체가 응답 전체다. 응답의 첫 줄은 템플릿의 첫 줄이다.
- 템플릿 바깥을 코드 블록(```)으로 감싸지 않는다. 본문, 보고서처럼 템플릿 안에 있는 코드 블록만 쓴다.
- 마무리 안내의 push 줄 끝 "(경고: <핵심 줄>)"은 push는 됐지만 git이 경고나 오류를 출력했을 때만 쓴다. 예: upstream 설정 실패
- 브랜치 이름, 파일 경로, 해시, PR 번호는 git과 gh가 출력한 값을 그대로 옮긴다.
- `다음:` 줄은 스킬이 끝난 뒤 읽는 쪽이 할 행동이다. 질문이 아니며, 스킬은 답을 기다리지 않는다. 행동은 "~ 후 다시 요청", "<스킬>로 ~"처럼 동작으로 쓴다. 조건에 따라 갈리면 조건을 앞에 짧게 쓴다.

## 모드

| 모드 | 호출 | 동작 |
|---|---|---|
| 확인 (기본) | `/git-kit:pr-writer` 또는 "PR 만들어줘" | 준비를 마친 뒤 마지막에 한 번만 확인받고 push와 PR 생성을 한다 |
| 자동 | `/git-kit:pr-writer --auto` | 확인 없이 push하고 PR을 Draft로 만든다 |

- 인자에 `--auto`가 그대로 있을 때만 자동 모드다. 그 밖의 모든 경우는 확인 모드다. 나머지 글자는 대화 맥락으로 본다. 누가 호출했는지로 모드를 추측하지 않는다.
- 두 모드 모두 진행 중에 중간 질문을 하지 않는다. 스스로 정할 수 있는 것은 아래 기본값으로 정하고, 마무리 안내에 알린다.
- Draft 해제(검토 요청)는 어느 모드에서도 이 스킬이 하지 않는다. 결정 대기 PR의 Draft 해제는 decision-resolver가 확인받고 한다.

### 1. 준비

다음 순서로 확인하고, 처음 걸리는 항목을 처리한다.

1. **GitHub 접근 방법**
   - `gh auth status`가 성공하면 gh를 쓴다.
   - 아니면 GitHub MCP 도구가 연결돼 있으면 그것을 쓴다.
   - 둘 다 없으면 링크 안내로 진행한다. push(확인 모드는 확인 후) 뒤 `https://github.com/<저장소>/pull/new/<브랜치>` 링크와 함께 제목, 본문, 보고서 코멘트를 복사할 수 있게 보여주고 끝낸다.
2. **저장소 주소**: `gh repo view --json nameWithOwner`로 `<저장소>`(소유자/이름)를 얻는다. gh를 쓸 수 없으면 `git config --get remote.origin.url`에서 뽑는다. `git remote get-url`은 주소 변환 설정이 적용된 값을 보여줄 수 있어 쓰지 않는다.
3. **현재 브랜치**: detached HEAD이거나 보호 브랜치(main, master, 기본 브랜치)면 PR을 만들지 않고 아래 "PR을 만들지 않을 때" 템플릿으로 알린 뒤 끝낸다.
4. **원격 최신화**
   - `git fetch origin`으로 원격 정보를 받는다.
   - 기본 브랜치는 `origin/HEAD`에서 `origin/`을 뗀 이름이다. 없으면 `gh repo view --json defaultBranchRef`로 찾는다.
   - 현재 브랜치가 base 브랜치보다 뒤처진 커밋 수(`git rev-list --count HEAD..origin/<base 브랜치>`)를 기록해 둔다. base 브랜치는 보통 기본 브랜치이고, 8단계에서 바뀌면 다시 센다. 여기서 머지하지 않는다.
   - 뒤처졌을 때 확인 모드는 마지막 확인의 선택지에 "base 브랜치를 먼저 머지"를 넣는다. 자동 모드는 머지하지 않고 보고서 코멘트의 Please check에 "<base 브랜치>보다 <n>커밋 뒤처짐. 머지 전 최신화 필요"를 적는다.
5. **PR에 올릴 커밋**: `git log --oneline origin/<기본 브랜치>..HEAD`가 비어 있으면 아래 "PR을 만들지 않을 때" 템플릿으로 알리고 끝낸다.
6. **커밋 안 된 변경**: 있으면 기록해 둔다. PR에 들어가지 않는다는 사실을 마무리 안내(확인 모드는 마지막 확인)에 알린다.
7. **기존 PR**: `gh pr view --json number,url,isDraft,baseRefName,title`로 현재 브랜치의 열린 PR을 찾는다. 있으면 갱신으로 진행하고, 그 PR의 base(`baseRefName`)를 base 브랜치로 쓴다. base가 기본 브랜치가 아니면 4·5단계를 그 기준으로 다시 센다.
8. **쌓인 브랜치**: 새 PR이면, 현재 브랜치가 아직 머지되지 않은 다른 열린 PR의 브랜치 위에 쌓였는지 확인한다.
   - `gh pr list --state open --json number,headRefName`으로 열린 PR을 찾고, 각 브랜치에 대해 `git merge-base --is-ancestor origin/<그 브랜치> HEAD`가 성공하는지 본다.
   - 해당하는 PR이 있으면 base를 그 PR의 브랜치로 둔다. 여러 개면 현재 브랜치에 가장 가까운(커밋이 가장 많이 쌓인) 것을 고른다.
   - 결정 대기 PR이면 이 단계 대신 `references/decision-pending.md`의 base 규칙을 따른다. gh와 GitHub MCP가 모두 없으면 건너뛴다.
   - base가 기본 브랜치가 아니게 되면, 올릴 커밋(5단계)과 뒤처진 커밋 수(4단계)를 base 브랜치 기준으로 다시 센다. 기본 브랜치를 따라잡는 일은 아래에 있는 PR이 할 일이므로, 기본 브랜치 기준 뒤처짐은 알리지 않는다.
9. **참조 파일**
   - `refs/git-kit/decisions/<현재 브랜치>`가 있으면 `references/decision-pending.md`를 읽는다.
   - 저장소에 PR 템플릿이 있으면 `references/repo-pr-template.md`를 읽는다.
   - base가 열린 PR의 작업 브랜치(쌓인 PR)면 `${CLAUDE_PLUGIN_ROOT}/shared/report.md`의 "머지 순서"를 읽는다.

#### PR을 만들지 않을 때

```
PR 만들지 않음 · <이유>
현재 브랜치: <현재 브랜치> (<base 브랜치>보다 앞선 커밋 0개)
PR에 들어가지 않는 변경: <파일>
다음: <다음에 할 일>
```

| <이유> | 다음 |
|---|---|
| 보호 브랜치 | 작업 브랜치로 옮긴 뒤 다시 요청 |
| detached HEAD | 작업 브랜치로 옮긴 뒤 다시 요청 |
| 올릴 커밋 없음 | 이 브랜치에 커밋한 뒤 다시 요청 |

- "현재 브랜치"의 괄호는 "올릴 커밋 없음"일 때만 쓴다. detached HEAD면 "현재 브랜치" 줄을 쓰지 않는다.
- "PR에 들어가지 않는 변경"은 "올릴 커밋 없음"이고 커밋 안 된 변경이 있을 때만 쓴다.

### 2. 제목과 본문

PR에 올릴 커밋 전체(`origin/<base 브랜치>..HEAD`)를 기준으로 쓴다. 마지막 커밋 하나나 브랜치 이름만 보고 쓰지 않는다.

#### 제목

`<이모지> <type>: <description>`

- **type**: 브랜치 전체의 주된 목적을 고른다. feat와 fix가 헷갈리면 fix를 쓴다. 결정 대기 PR이면 `references/decision-pending.md`를 따른다.
- **description**: 영어, 명령형 현재 시제 동사로 시작하는 소문자, 마침표 없음. 이모지부터 끝까지 72자 이하로 쓴다. 어떤 파일을 고쳤는지가 아니라 무엇이 달라졌는지를 쓴다.

type과 이모지는 `${CLAUDE_PLUGIN_ROOT}/shared/commit-types.md`를 읽고 따른다.

#### 본문

저장소에 PR 템플릿이 있으면 `references/repo-pr-template.md`를 따른다. 없으면 아래 템플릿을 쓴다.

```
## Summary
<무엇이 달라졌는지 한두 문장, 개조식>

## Changes
- <커밋 메시지>
```

- **Summary**: 대화 맥락의 작업 내용과 커밋 전체를 보고, 사용하는 쪽에서 무엇이 달라졌는지를 한국어 개조식으로 쓴다. 구현 방법을 늘어놓지 않는다.
- **Changes**: 커밋 메시지를 오래된 것부터 한 줄씩 그대로 옮긴다. 기본 브랜치를 머지한 커밋(Merge …)은 넣지 않는다.

#### 기존 PR을 갱신할 때

- 제목과 Summary, Changes는 지금 커밋 전체를 기준으로 다시 쓴다.
- 그 밖에 사람이 본문에 더한 내용(섹션, 링크, 이슈 번호 등)은 지우지 않고 그대로 둔다.

### 3. 보고서 코멘트

AI가 판단한 것과 사람이 확인할 것을 PR 첫 코멘트에 보고서로 쓴다. 보고서는 AI 자신의 작업 보고다. 대화 맥락에 있는 이번 작업에서 AI가 고른 것과 확신하지 못한 것만 쓴다. 커밋 내용을 리뷰해서 문제를 찾아 적지 않는다. 결정 대기 PR이면 `references/decision-pending.md`대로 결정 부분을 맨 앞에 두고, 그 뒤는 아래 템플릿 그대로 쓴다.

```
<!-- git-kit:report -->
## Decisions made
- 가장 어려운 결정: <정한 것과 이유, 개조식> <위치>
- 버린 대안: <버린 것과 이유, 개조식> <위치>

## Please check
- [ ] <사람이 확인할 것, 개조식> <위치>
- [x] <확인을 마친 것, 개조식> <위치>
  - 확인 결과: [<결과>](<결과 코멘트 링크>)
```

- 첫 줄의 `<!-- git-kit:report -->`는 이 코멘트를 다시 찾기 위한 표시다. 항상 그대로 둔다.
- **Decisions made**: 작업 중 AI가 여러 선택지 중 하나를 골랐을 때만 쓴다. "가장 어려운 결정"과 "버린 대안"은 각각 있을 때만 쓴다.
- **Please check**: 아래 중 해당하는 것만 쓴다.
  - AI가 확신하지 못하는 부분
  - AI가 만든 화면, 문구처럼 사람이 직접 봐야 하는 것
  - 자동 모드에서 base 브랜치보다 뒤처졌을 때의 최신화 필요
  - 일반 쌓인 PR의 머지 순서. 형식과 순서는 `${CLAUDE_PLUGIN_ROOT}/shared/report.md`의 "머지 순서"를 따른다. 결정 대기 PR은 결정 부분에 쓰므로 여기에 쓰지 않는다.
- **후속 작업은 쓰지 않는다**: 이번 PR에서 일부러 하지 않은 일(다음 PR에서 할 일, 다른 브랜치나 문서의 할 일)은 확인할 것이 아니라 할 일이다. Decisions made와 Please check에 쓰지 않는다. 후속 작업은 부른 쪽이 관리한다.
- **맥락이 없을 때**: 작업 맥락 없이 불렸다면 Decisions made와 Please check를 쓰지 않는다. 아래 세 가지만 예외다.
  - 자동 모드에서 base 브랜치보다 뒤처졌을 때의 안내
  - 저장소 PR 템플릿을 채우며 생긴 항목("작성 필요", "확인 필요"). `references/repo-pr-template.md`를 따른다.
  - 일반 쌓인 PR의 머지 순서
- 기존 보고서가 있으면 "맥락이 없을 때" 규칙 대신 "기존 보고서가 있을 때"를 따른다.
- 두 섹션이 모두 비면 보고서 코멘트를 만들지 않는다.

#### 위치 표기

`<위치>`는 코드 위치가 의미 있는 항목에만 붙인다.

- 형식: `` [`<경로>:<줄>`](https://github.com/<저장소>/blob/<커밋 해시>/<경로>#L<줄>) ``. 여러 줄이면 `<경로>:<시작>-<끝>`과 `#L<시작>-L<끝>`, 파일 전체면 줄 번호를 뺀다.
- 경로는 저장소 루트 기준의 전체 경로다. 커밋 해시는 push할 HEAD의 해시다.
- 1곳이면 항목 문장 끝에 한 칸 띄우고 붙인다.
- 2곳 이상이면 항목 아래에 `- 관련 위치:` 하위 목록으로 쓰고, 위치마다 그곳의 역할을 짧게 붙인다. 3곳까지 쓰고 나머지는 "외 <n>곳"으로 줄인다.

#### 기존 보고서가 있을 때

PR 코멘트 중 `<!-- git-kit:report -->`로 시작하는 것을 찾아 그 코멘트를 고친다. 새 코멘트를 더 달지 않는다.
이번 내용을 덧붙이지 않는다. 기존 보고서의 항목을 하나씩 아래 기준으로 다시 정한 뒤, PR 전체 기준으로 다시 쓴다.

항목 종류는 섹션이 아니라 항목마다 문구로 정한다.

| 종류 | 알아보는 법 | 다시 쓸 때 |
|---|---|---|
| 상태 항목 | Please check 항목의 문구가 `<브랜치>보다 <n>커밋 뒤처짐. 머지 전 최신화 필요`, `<섹션 이름> 작성 필요`, `<항목> 확인 필요`, `머지 순서: …` 중 하나 | 맥락과 상관없이 지금 상태로 다시 계산한다. 해결됐으면 빼고, 숫자나 브랜치가 바뀌었으면 고친다 |
| 판단 항목 | 그 밖의 모든 항목(Decisions made, 상태 항목이 아닌 Please check) | 대화 맥락이 있으면 지금 코드에 비춰 아래 "확인한 항목과 필요 없어진 항목"대로 다시 정한다. 맥락이 없으면 확인할 수 없으므로 그대로 둔다 |

- 결정 대기 PR의 결정 부분(결정 표시 안쪽)은 다시 쓰지 않는다. 한 글자도 바꾸지 않고 그대로 옮긴다. 고치는 것은 decision-resolver의 일이다.
- 이번 작업에서 생긴 항목을 더한다.
- 남는 항목은 사람이 체크한 상태(`[x]`)를 그대로 옮긴다.
- **확인한 항목과 필요 없어진 항목**: Please check의 판단 항목은 두 경우를 나눈다.
  - 확인을 마친 항목은 지우지 않는다. `[x]`로 바꾸고 항목 아래에 `- 확인 결과: <결과>`를 쓴다. 결과를 적은 PR 코멘트가 있으면 그 링크를 붙인다. 결과 코멘트가 가리킬 항목이 보고서에 남고, 무엇을 확인했는지 PR에서 바로 보이게 하기 위해서다.
  - 코드가 바뀌어 더 확인할 필요가 없어진 항목만 지운다.
  - `[x]`인 항목은 다음 갱신에서도 그대로 둔다.
- 다시 쓴 결과가 기존 보고서와 같으면 고치지 않는다.
- 다시 쓴 결과에 남는 항목이 없으면 코멘트를 지우지 않고 아래 내용으로 고친다. 지우면 수정 이력까지 사라지기 때문이다. 나중에 항목이 다시 생기면 이 코멘트를 다시 고쳐 쓴다. 결정 부분이 있으면 이렇게 고치지 않는다. 결정 부분은 그대로 두고 빈 섹션만 뺀다.
  ```
  <!-- git-kit:report -->
  남은 항목 없음
  ```
- 이전 내용은 GitHub 코멘트의 수정 기록에 남으므로 따로 쌓아 두지 않는다.

### 4. 확인과 push

#### 바뀐 내용이 없을 때

기존 PR 갱신인데 올릴 커밋이 없고, 새로 쓴 제목, 본문, 보고서가 지금 PR과 같으면 고치지 않는다. 모드와 상관없이 묻지 않고 아래로 알린 뒤 끝낸다.

```
PR 갱신하지 않음 · 바뀐 내용 없음
#<PR 번호> <PR 링크>
```

#### 확인 (확인 모드만)

원격 저장소(GitHub)를 바꾸는 작업, 즉 push, PR 생성과 갱신, 보고서 코멘트 작성을 하기 전에 아래 질문을 한 번만 한다. 그 전 단계(준비, 제목과 본문 작성, 보고서 작성)는 로컬에서만 하므로 묻지 않는다. 자동 모드는 이 단계를 건너뛴다.

```
PR 준비 완료 · <현재 브랜치> → <base 브랜치>

제목: <제목>
push할 커밋: <개수>개
기존 PR: #<번호> 갱신
PR 템플릿: <파일> (다른 후보: <파일>, <파일>)
쌓인 PR: #<번호> 위 (그 PR 머지 후 base를 <기본 브랜치> 브랜치로 변경)
뒤처짐: <base 브랜치>보다 <개수>커밋
PR에 들어가지 않는 변경: <파일>
보고서 코멘트: <섹션> <항목 수>, <섹션> <항목 수>
PR 만드는 방법: 링크 안내 (gh 로그인과 GitHub MCP 없음)

어떻게 진행할까요? 번호로 답해 주세요.
1. push하고 PR <만들기|갱신하기>
2. <base 브랜치> 브랜치를 먼저 머지한 뒤 push하고 PR <만들기|갱신하기>
3. 미리 보기
4. 취소

제목이나 본문을 바꾸고 싶으면 말씀해 주세요.
```

- "push할 커밋"부터 "PR 만드는 방법"까지는 있을 때만 쓴다. "PR 만드는 방법" 줄은 링크 안내로 진행할 때만 쓴다.
- 기존 보고서를 "남은 항목 없음"으로 고칠 때는 "보고서 코멘트" 줄을 `보고서 코멘트: 남은 항목 없음`으로 쓴다.
- 선택지 문구는 접근 방법과 상관없이 그대로 쓴다. 링크 안내일 때도 1번은 "push하고 PR 만들기"다.
- 2번 선택지는 base 브랜치보다 뒤처졌을 때만 넣는다. 선택지 번호는 보이는 순서대로 다시 매긴다.
- 선택지 목록과 마지막 안내 줄 사이에는 빈 줄을 둔다. 빈 줄이 없으면 마크다운에서 안내 줄이 마지막 선택지에 붙어 보이기 때문이다.
- "미리 보기"를 고르면 제목, 본문, 보고서 코멘트(있을 때) 전체를 보여준 뒤 같은 질문을 다시 한다. 이때 "미리 보기" 자리에 "Please check 먼저 처리"를 넣는다. 이미 본 미리 보기를 다시 고를 일은 없고, 미리 보기를 고르는 건 보통 Please check를 올리기 전에 처리하고 싶어서이기 때문이다.
  - 체크 안 된 판단 항목이 없으면 "Please check 먼저 처리"를 넣지 않는다. 상태 항목(뒤처짐, 머지 순서 등)은 PR을 만들기 전에 처리할 수 없으므로 세지 않는다.
  - "Please check 먼저 처리"를 고르면 push, PR 생성과 갱신, 보고서 코멘트 작성을 하지 않고 "6. 마무리 안내"의 "Please check 먼저 처리를 골랐을 때"로 알린 뒤 끝낸다. 항목 처리는 부른 쪽이 한다. 코드를 고쳐야 하면 고친 뒤 commit-writer로 커밋하고 pr-writer를 다시 부른다.
- 사용자가 제목이나 내용을 고쳐 달라고 하면 반영한 뒤 같은 질문을 다시 한다.
- 사용자가 Please check의 판단 항목을 확인했다고 하면, 그 항목을 `[x]`로 바꾸고 아래에 `- 확인 결과: <사용자가 말한 결과>`를 쓴 뒤 같은 질문을 다시 한다.
- "base 브랜치를 먼저 머지"를 고르면 `git merge origin/<base 브랜치>`로 머지한다. 충돌이 나면 `git merge --abort`로 되돌리고, 충돌 파일을 알린 뒤 끝낸다.

#### push

- 올릴 커밋이 없으면(원격 브랜치가 있고 `git rev-list --count origin/<현재 브랜치>..HEAD`가 0) push를 건너뛴다.
- push 직전에 `git branch --show-current`로 현재 브랜치를 다시 확인한다. 준비 때 본 브랜치와 다르거나 보호 브랜치면 push하지 않고 알린다.
- 저장소 지침(CLAUDE.md 등)에 push 전 요구사항(테스트 통과 등)이 있으면 따른다. 충족하지 못하면 push하지 않고 무엇이 부족한지 알린다.
- `git push -u origin HEAD`로 push한다.
- `--force`, `--force-with-lease`는 쓰지 않는다. push가 거부되면(원격에 없는 커밋이 있는 경우 등) 멈추고 알린다.

### 5. PR 만들기와 갱신

본문과 보고서 코멘트는 저장소 밖의 임시 파일(`$TMPDIR` 아래)에 쓴 뒤 파일로 넘긴다. 따옴표나 줄바꿈이 셸에서 깨지지 않게 하고, 임시 파일이 커밋되지 않게 하기 위해서다. 아래는 gh 기준이며, GitHub MCP를 쓸 때는 같은 일을 하는 도구를 쓴다.

#### 새 PR

```bash
gh pr create --base <base 브랜치> --title '<제목>' --body-file <본문 파일> [--draft]
gh pr comment <PR 번호> --body-file <보고서 파일>
```

- base는 기본 브랜치다. 쌓인 브랜치면 "1. 준비" 8단계에서 고른 브랜치이고, 결정 대기 PR이면 `references/decision-pending.md`를 따른다.
- 자동 모드면 `--draft`를 붙인다. 결정 대기 PR은 모드와 상관없이 Draft로 만든다.
- 보고서 코멘트는 보고할 내용이 있을 때만 단다.

#### 기존 PR 갱신

```bash
gh pr edit <PR 번호> --title '<제목>' --body-file <본문 파일>
```

- 보고서 코멘트는 `<!-- git-kit:report -->`로 시작하는 코멘트를 찾아 고친다. 찾지 못하면 새로 단다.
  ```bash
  gh api repos/<저장소>/issues/<PR 번호>/comments --paginate \
    --jq '.[] | select(.body | startswith("<!-- git-kit:report -->")) | .id'
  gh api -X PATCH repos/<저장소>/issues/comments/<코멘트 id> -F body=@<보고서 파일>
  ```
- Draft 상태는 바꾸지 않는다. Draft인 PR은 Draft로, 아닌 PR은 그대로 둔다. 결정 대기 PR의 Draft 해제는 decision-resolver가, 그 밖의 Draft 해제는 사람이 한다.

#### 실패했을 때

gh 명령이 실패하면 같은 명령을 반복하지 않는다. 오류 메시지와 어디까지 됐는지(push 여부, PR 생성 여부)를 마무리 안내로 알리고 끝낸다.

### 6. 마무리 안내

끝나면 결과를 한 번에 알린다. 해당하는 내용이 없는 줄은 쓰지 않는다.

#### 정상 종료

```
PR <생성|갱신> 완료 · #<PR 번호>
<PR 링크>

제목: <제목>
상태: <Draft|Open> · <현재 브랜치> → <base 브랜치>
push: 커밋 <개수>개 (경고: <핵심 줄>)
보고서 코멘트: <섹션> <항목 수>, <섹션> <항목 수>
쌓인 PR: #<번호> 위 (그 PR 머지 후 base를 <기본 브랜치> 브랜치로 변경)
뒤처짐: <base 브랜치>보다 <개수>커밋
PR에 들어가지 않는 변경: <파일>
```

- "push"는 이번에 push한 커밋이 있을 때만 쓴다.
- "쌓인 PR"은 base가 다른 PR의 브랜치일 때만 쓴다.
- 기존 보고서를 "남은 항목 없음"으로 고쳤으면 "보고서 코멘트" 줄을 `보고서 코멘트: 남은 항목 없음`으로 쓴다.
- "뒤처짐"은 머지하지 않고 PR을 만든 경우에만 쓴다.

#### Please check 먼저 처리를 골랐을 때

```
PR <생성|갱신> 보류 · Please check 먼저 처리

남은 항목
- <체크 안 된 판단 항목>

다음: 항목을 처리한 뒤 다시 요청
```

- "남은 항목"은 체크 안 된 판단 항목의 문장을 그대로 옮긴다. 위치 링크와 하위 목록은 옮기지 않는다.
- 부른 쪽이 AI일 때도 무엇을 처리할지 알 수 있게 항목을 모두 쓴다.

#### 링크 안내 (gh와 GitHub MCP가 모두 없을 때)

````
PR 링크 안내 · <현재 브랜치> → <base 브랜치>
push: 커밋 <개수>개 (경고: <핵심 줄>)
Draft로 만들어 주세요 (<결정 대기 PR|자동 모드>)

아래 링크에서 PR을 만들어 주세요.
https://github.com/<저장소>/pull/new/<현재 브랜치>

제목:
<제목>

본문:
```
<본문>
```

보고서 코멘트 (PR을 만든 뒤 첫 코멘트로 붙여 주세요):
```
<보고서>
```
````

- "보고서 코멘트"는 보고할 내용이 있을 때만 쓴다.
- "Draft로 만들어 주세요" 줄은 Draft로 만들어야 하는 PR일 때만 쓴다. 결정 대기 PR이거나 자동 모드일 때다. 둘 다면 "결정 대기 PR"을 쓴다.

#### 실패하거나 멈췄을 때

```
PR <생성|갱신> 중단 · <멈춘 이유>

push: <완료|안 함> (경고: <핵심 줄>)
PR: <#<PR 번호> 생성됨|안 만듦>
실패 원인: <오류 메시지 핵심 줄>
```

- <멈춘 이유>는 "push 거부", "push 전 요구사항 미충족", "base 브랜치 머지 충돌", "gh 오류", "사용자 취소" 중 하나다.
- "실패 원인"은 오류가 있을 때만 쓴다. 출력 전체를 붙이지 않고 핵심 줄만 옮긴다.
- 보호 브랜치, detached HEAD, 올릴 커밋 없음처럼 시작 전에 멈추는 경우는 이 템플릿 대신 "1. 준비"의 "PR을 만들지 않을 때" 템플릿을 쓴다.
