# 결정 대기 변경 분리 절차

결정이 필요한 변경이 끝난 작업을 막지 않도록 따로 떼어내는 절차다. 결정을 어떻게 구현할지는 정하지 않는다. git으로 나누고 기록하는 일만 한다.

## 언제 읽는가

커밋할 변경 중에 사람의 결정이 있어야 완성되는 변경(이하 결정 대기 변경)이 섞여 있을 때 읽는다.

- 사용자가 "이건 아직 결정 안 됐어"처럼 알려준 경우
- 작업 중인 AI가 사람의 답이 필요한 지점을 만났다고 판단한 경우

결정이 필요 없는 일반 변경만 있으면 읽지 않는다.

## 절차

1. **나누기**: 변경 파일을 "결정 대기"와 "그 외"로 나눈다. 파일 단위로만 나눈다. 한 파일에 둘이 섞여 있으면 결정 대기 쪽에 넣고 "섞인 파일"로 알린다. 결정이 안 된 코드가 커밋되는 것보다 일부 완료된 코드가 늦게 커밋되는 쪽이 안전하기 때문이다.
2. **결정할 것 정리**: 대화 맥락(사용자가 말한 미결 사항, AI가 만난 질문)에서 아래를 정리한다. 이 맥락은 세션이 끝나면 사라지므로, 지금 정리해서 6번 단계의 기록에 남긴다.
   - 결정할 것: 한 문장
   - 미결정 이유: AI가 정하지 않은 이유, 개조식
   - 선택지: 2~4개와 각각의 장단점, 개조식. 추천은 정확히 하나에만 "(추천)"을 붙이고 맨 위에 둔다.
3. **확인**: 확인 모드는 두 묶음과 결정할 것을 보여주고 확인받는다. 자동 모드는 바로 진행한다.
4. **그 외 커밋**: "그 외" 변경을 SKILL.md의 "2. 변경 분할"부터 "4. 확인과 커밋"까지의 규칙대로 지금 브랜치에 커밋한다.
5. **새 브랜치 만들기**: 결정 대기 변경을 들고 새 브랜치를 만든다. 이름은 SKILL.md의 "브랜치 이름" 규칙을 따른다.
   - 결정 대기 변경이 방금 커밋한 작업에 의존하면 → 지금 브랜치에서 딴다. `git switch -c <이름>`
   - 의존하지 않으면 → 로컬 기본 브랜치에서 딴다. `git switch -c <이름> <기본 브랜치>`
   - 의존하는지 애매하면 지금 브랜치에서 딴다. 그 위에서 따면 항상 동작하기 때문이다.
   - 기본 브랜치에서 따다가 커밋 안 된 변경과 부딪혀 git이 거부하면, 지금 브랜치에서 따고 그 사실을 알린다.
6. **결정 대기 기록**: 새 브랜치의 결정 대기 정보를 git ref로 남긴다. pr-writer, decision-resolver, branch-cleaner가 이 기록으로 결정 대기 브랜치를 알아본다.
   - 위치: `refs/git-kit/decisions/<브랜치 이름>`. 파일을 직접 쓰지 않고 git 명령으로만 다룬다. `.git` 폴더는 Claude Code의 보호 경로라 파일을 직접 쓰면 권한 확인에 막히기 때문이다. 이 ref는 기본 push 대상이 아니라 원격에 올라가지 않고, worktree끼리 공유된다.
   - 내용:
     ```
     결정할 것: 로그인 실패 몇 회에 계정을 잠글지
     따온 브랜치: feat/login-email-validation
     기록한 날: 2026-10-21
     미결정 이유: 기획 문서에 기준 없음. 보안과 사용성 사이 제품 판단 필요.
     선택지:
     - 5회 (추천): 일반적인 기준. 무차별 대입 방어에 충분.
     - 10회: 오타가 잦은 사용자에게 관대함. 방어력은 낮아짐.
     ```
   - 관련 위치는 기록하지 않는다. 코드에서 다시 찾을 수 있고, 커밋이 쌓이면 줄 번호가 바뀌기 때문이다.
   - 기록: 한 줄씩 인자로 넘겨 따옴표와 줄바꿈이 깨지지 않게 한다.
     ```bash
     printf '%s\n' \
       '결정할 것: <결정할 것>' \
       '따온 브랜치: <따온 브랜치>' \
       '기록한 날: <YYYY-MM-DD>' \
       '미결정 이유: <미결정 이유>' \
       '선택지:' \
       '- <선택지> (추천): <장단점>' \
       '- <선택지>: <장단점>' \
       | git hash-object -w --stdin \
       | xargs git update-ref refs/git-kit/decisions/<브랜치 이름>
     ```
   - 같은 ref가 이미 있으면 덮어쓴다. 같은 이름의 브랜치가 지워진 뒤 남은 오래된 기록이기 때문이다.
   - 기록한 뒤 `git cat-file -p refs/git-kit/decisions/<브랜치 이름>`으로 다시 읽어 확인한다. 기록에 실패해도 커밋과 분리는 그대로 진행하고, 마무리 안내에 "기록 실패 줄"을 더한다. 성공하면 안내에 쓰지 않는다.
   - commit-writer는 이 기록을 만들기만 하고 지우지 않는다. 결정 대기 브랜치에서 커밋을 이어서 해도 커밋만으로는 결정이 났는지 알 수 없기 때문이다. 지우는 일은 decision-resolver(모든 결정 반영 시)와 branch-cleaner(브랜치가 사라진 기록 정리)가 맡는다.
7. **모드별 처리**
   - 확인 모드: 결정 대기 변경을 커밋하지 않는다. 새 브랜치로 옮겨만 둔다.
   - 자동 모드: 새 브랜치에서 지금 상태 그대로 커밋한다. 다른 브랜치로 옮겨 다닐 때 변경이 따라오지 않게 하기 위해서다. 메시지는 SKILL.md의 "3. 메시지 작성" 규칙을 따르고, "wip", "draft" 같은 표시 대신 지금 코드가 하는 일을 쓴다. 결정 대기 상태는 PR 제목과 본문이 보여준다.

## 분리 후 안내

SKILL.md의 "5. 마무리 안내" 대신 아래 템플릿을 쓴다. 템플릿 규칙은 SKILL.md의 "안내 언어와 형식"을 따른다. 섞인 파일, 제외됨 같은 SKILL.md 정상 종료 템플릿의 나머지 줄은 해당할 때 맨 아래에 그대로 붙인다.

- 커밋 줄은 커밋마다 하나씩 쓴다.
- "임시 구현"은 결정 대기 변경에 임시로 넣은 값이나 동작이 있을 때만 쓴다. 코드를 고치거나 판단하지 않고, 보이는 그대로 한 줄로 쓴다.
- "기록 실패"는 6번 단계의 기록에 실패했을 때만 맨 아래에 붙인다. 기록에 성공한 사실은 쓰지 않는다.

### 확인 모드

```
커밋 완료 (<커밋 수>개) · 결정 대기 변경 <건수>건은 커밋하지 않고 새 브랜치로 옮김

<원래 브랜치>
- <해시 7자리> <커밋 메시지>

<새 브랜치> · 결정 대기  ← 현 위치
- 결정할 것: <결정할 것>
- 따온 브랜치: <따온 브랜치> (<따온 이유>)
- 옮긴 파일: <파일>
- 임시 구현: <임시로 넣은 값이나 동작> (<파일>:<줄>)
- 결정 사항을 해결한 뒤 이 브랜치에서 커밋을 이어서 진행해 주세요.

다음에 할 수 있는 일
1. 결정이 났다면: 현 위치에서 결정 사항을 반영하고 커밋해요.
2. 결정을 기다리는 동안 원래 작업을 하려면: 옮긴 파일을 먼저 커밋하거나 stash한 뒤 원래 브랜치로 이동해요.
   git switch <원래 브랜치>
   커밋이나 stash 없이 이동하면 옮긴 파일의 변경이 함께 따라가요.
```

### 자동 모드

```
커밋 완료 (<커밋 수>개, 브랜치 2개)

<원래 브랜치>
- <해시 7자리> <커밋 메시지>

<새 브랜치> · 결정 대기  ← 현 위치
- <해시 7자리> <커밋 메시지>
- 결정할 것: <결정할 것>
- 따온 브랜치: <따온 브랜치> (<따온 이유>)
- 임시 구현: <임시로 넣은 값이나 동작> (<파일>:<줄>)
- 결정 사항을 해결한 뒤 이 브랜치에서 커밋을 이어서 진행해 주세요.

두 브랜치 모두 커밋돼 있어 어느 쪽으로든 바로 이동할 수 있어요.
```

### 기록 실패 줄

```
기록 실패: 결정 대기 기록을 남기지 못했어요 (<이유>). branch-cleaner가 이 브랜치를 결정 대기로 알아보지 못할 수 있어요.
```
