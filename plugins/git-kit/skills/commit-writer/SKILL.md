# Commit Writer

AI가 규칙대로 작업하며 git에 읽기 좋은 기록을 남기고, 사람은 PR에서 검토하게 돕는 스킬이다. git 히스토리는 AI가 한 작업의 일지가 되므로, 커밋 하나는 주제 하나만 담고 히스토리만 읽어도 무엇을 했는지 알 수 있어야 한다. 로컬 커밋은 언제든 되돌릴 수 있어 자유롭게 하되, push처럼 밖으로 나가는 일은 이 스킬에서 하지 않는다.

## 핵심 원칙

- **기록한다.** 커밋 하나에 주제 하나만 담는다. 히스토리만 읽어도 작업 흐름이 보이게 한다.
- **로컬까지만 한다.** 이 스킬은 커밋까지만 한다. push와 PR 생성은 pr-writer가 맡는다.
- **결정 대기를 분리한다.** 결정이 필요한 변경이 끝난 작업을 막지 않도록 따로 떼어낸다.
- **의도와 비밀값을 지킨다.** 사용자가 미리 stage한 파일을 존중하고, 비밀값 파일은 커밋하지 않는다. 문제가 생기면 우회하지 않고 멈춘다.
- **git 작업만 한다.** 코드를 어떻게 고칠지는 정하지 않는다.

## 모드

| 모드 | 호출 | 동작 |
|---|---|---|
| 확인 (기본) | `/git-kit:commit-writer` 또는 "커밋해줘" | 커밋 하나마다 파일과 메시지를 보여주고 확인받은 뒤 커밋한다 |
| 자동 | `/git-kit:commit-writer --auto` | 확인 없이 브랜치 생성, 분할, 커밋을 끝까지 진행하고 결과만 알린다 |

- 인자(`$ARGUMENTS`)에 `--auto`가 그대로 있을 때만 자동 모드다. 그 밖의 모든 경우는 확인 모드다. 나머지 글자는 대화 맥락으로 본다. 누가 호출했는지로 모드를 추측하지 않는다.
- 자동 모드는 중간에 멈추지 않는다. pre-commit hook이 실패하면 `--no-verify`로 우회하지 않고, 실패한 파일과 오류를 보고한 뒤 끝낸다. 수정과 재시도는 호출한 쪽이 한다.
- 자동 모드에서 미리 stage된 파일에 비밀값 파일이 있으면, 묻지 않고 stage를 해제해 커밋에서 뺀다. 비밀값 파일 커밋은 사람이 직접 한다.

## 안내 언어와 형식

분할안, 확인 질문, 마무리 안내처럼 사용자에게 보여주는 글은 한국어로 쓴다. 커밋 메시지와 브랜치 이름만 영어로 쓴다.

분할안과 마무리 안내는 이 문서와 `references/decision-split.md`의 템플릿을 그대로 따른다.

- `<…>` 자리만 채운다. 라벨, 기호, 줄 순서는 바꾸지 않는다.
- "있을 때만" 줄은 해당할 때만 쓰고, 없으면 줄째 뺀다.
- 굵게(`**`) 같은 꾸밈이나 템플릿에 없는 줄을 더하지 않는다.
- 템플릿 앞뒤에 문장(참고, 설명, 이유, 다음에 할 일)을 덧붙이지 않는다. 알릴 것은 템플릿의 줄로만 알린다.
- 안내는 템플릿 자체가 응답 전체다. 응답의 첫 줄은 템플릿의 첫 줄이다.
- 템플릿 바깥을 코드 블록(```)으로 감싸지 않는다.
- 브랜치 이름, 파일 경로, 해시는 git이 출력한 값을 그대로 옮긴다. 단, 분할안과 그룹별 질문의 파일은 "4. 확인과 커밋"의 파일 이름 규칙을 따른다.
- `다음:` 줄은 스킬이 끝난 뒤 읽는 쪽이 할 행동이다. 질문이 아니며, 스킬은 답을 기다리지 않는다. 행동은 "~ 후 다시 요청", "<스킬>로 ~"처럼 동작으로 쓴다. 조건에 따라 갈리면 조건을 앞에 짧게 쓴다.

## 진행 순서

- [ ] 1. 상태 점검
- [ ] 2. 변경 분할
- [ ] 3. 메시지 작성
- [ ] 4. 확인과 커밋
- [ ] 5. 마무리 안내

### 1. 상태 점검

시작하면 아래 명령으로 현재 상태를 한 번에 파악한다.

- `git status --porcelain=v1 -b` : 브랜치, staged·unstaged·untracked 파일
- `git diff --cached --name-only` : 미리 stage된 파일
- `git log --oneline -5` : 최근 커밋 (첫 커밋 여부 판단용)

다음 순서로 확인하고, 처음 걸리는 항목을 처리한다.

1. **git 저장소가 아님** → 아래 "커밋하지 않을 때" 템플릿으로 알리고 끝낸다.
2. **merge·rebase·cherry-pick 진행 중** → 커밋하지 않고 "커밋하지 않을 때" 템플릿으로 알린 뒤 끝낸다. 충돌 해결은 이 스킬의 일이 아니다.
3. **커밋할 변경이 없음** → 오류가 아니다. "커밋하지 않을 때" 템플릿으로 알리고 끝낸다.
4. **브랜치 확인**
   - 보호 브랜치는 main, master, 저장소의 기본 브랜치(`origin/HEAD`에서 `origin/`을 뗀 이름), 설정 파일의 `protected-branches`다.
   - detached HEAD → 항상 새 브랜치를 만든다.
   - 보호 브랜치 → 새 브랜치를 만든다. 단, `.claude/git-kit.local.md`에 `allow-protected-commit: true`가 있으면 그대로 진행한다.
   - 이름은 아래 "브랜치 이름" 규칙을 따른다. 확인 모드는 분할안의 "새 브랜치" 줄로 이름을 보여주고, 분할안을 확인받은 뒤 만든다. 자동 모드는 바로 만든다.
   - 현재 위치에서 `git switch -c <이름>`으로 만든다. fetch·pull은 하지 않으며, 커밋 안 된 변경은 그대로 따라온다.
   - 보호 브랜치에 push 안 된 커밋(`git log origin/<기본 브랜치>..HEAD`)이 있으면 새 브랜치에 포함된다. 결과 안내에 그 개수와 목록을 알린다.
5. **미리 stage된 파일** → 사용자의 의도로 보고 1번 그룹 후보로 둔다. 그 안에 비밀값 파일이 있으면, 확인 모드는 분할안의 "비밀값 포함" 줄로 알리고 분할안과 함께 확인받으며, 자동 모드는 stage를 해제한다.
6. **제외 파일 분류** → 아래 파일은 어떤 그룹에도 넣지 않는다.
   - 비밀값: `.env`, `.env.*`(`.env.example` 제외), `*.pem`, `*.key`, `credentials.json` → 경고와 함께 "제외됨"에 표시
   - OS 전용: `.DS_Store`, `._*`, `Thumbs.db`, `desktop.ini` → 경고 없이 "제외됨"에만 표시

#### 커밋하지 않을 때

```
커밋하지 않음 · <이유>
현재 브랜치: <현재 브랜치>
다음: 진행 중인 작업을 끝내거나 중단한 뒤 다시 요청
```

- <이유>는 "git 저장소 아님", "<merge|rebase|cherry-pick> 진행 중", "커밋할 변경 없음" 중 하나다.
- "현재 브랜치"는 git 저장소일 때만, "다음"은 merge·rebase·cherry-pick 진행 중일 때만 쓴다.

#### 브랜치 이름

형식은 `<type>/<short-summary>`다. 새 브랜치와 결정 대기 브랜치 모두 같은 형식을 쓴다.

- **type**: `${CLAUDE_PLUGIN_ROOT}/shared/commit-types.md`의 type을 따른다. 이모지는 넣지 않는다. 작업의 주된 목적을 고른다.
- **summary**: 영어 소문자 kebab-case, 3~5단어 이내로 쓴다.
  - 근거는 대화 맥락의 작업 내용(사용자의 말, 명령어 뒤에 붙인 말, 받은 작업 지시)을 우선하고, 없으면 변경 내용(diff)을 본다.
  - 어떤 파일을 고쳤는지가 아니라 무엇이 달라졌는지를 쓴다.
  - "무엇을"만이 아니라 "무엇을 어떻게"까지, 같은 영역의 다른 작업과 겹치지 않을 만큼 구체적으로 쓴다.
  - 나쁨: `feat/login`, `fix/button`, `refactor/utils`, `feat/update-auth-tsx`
  - 좋음: `feat/login-email-validation`, `fix/submit-button-double-click`, `refactor/extract-form-error-utils`
- **이슈 번호**: 넣지 않는다.
- **결정 대기 브랜치**: 이름에 대기 표시를 넣지 않는다. 대기 상태는 PR 제목의 🚧와 보고서 코멘트의 WARNING이, 쌓인 위치는 PR의 base가 보여준다.
- **이름이 겹칠 때**: 끝에 `-2`, `-3`처럼 번호를 붙인다. 기존 브랜치로 옮겨가지 않는다.

### 2. 변경 분할

상태 점검에서 "제외됨"으로 분류한 파일을 뺀 나머지 변경(untracked 파일 포함)을 커밋 그룹으로 나눈다. 그룹 하나가 커밋 하나다.

- **기준**: 그룹 하나에 주제 하나만 담는다. 주제는 "하나의 이유로 함께 바뀐 변경"이다. 커밋 메시지 한 줄로 설명할 수 없으면 더 나눈다. 반대로 나눌지 애매하면 합친다. 나누는 기준은 "서로 다른 이유로 바뀌었는가"이지 "파일이 다른가"가 아니다.
- **단위**: 파일 단위로만 나눈다. 줄 단위 분할(`git add -p`)은 쓰지 않는다. 한 파일에 여러 주제가 섞여 있으면 주된 주제의 그룹에 넣고, 분할안에 "섞인 파일"로 알린다.
- **함께 다니는 파일**:
  - lock 파일(`package-lock.json`, `pnpm-lock.yaml`, `yarn.lock`)은 그 원인이 된 `package.json` 변경과 같은 그룹에 넣는다.
  - 새 기능이나 수정과 함께 쓴 테스트는 그 기능의 그룹에 넣는다. test 타입은 기존 코드의 테스트만 추가하거나 고칠 때 쓴다.
- **미리 stage된 파일**: 1번 그룹으로 둔다. 그 안에 주제가 섞여 보이면, 확인 모드는 분할을 제안하고 확인받으며, 자동 모드는 사용자의 의도로 보고 그대로 한 그룹으로 커밋한다.
- **관련 없는 변경 (자동 모드)**: 대화 맥락에 작업 내용이 분명히 있을 때만, 그 작업과 관련 없어 보이는 변경을 그룹에 넣지 않는다. 사용자가 하던 다른 작업일 수 있기 때문이다. 결과 안내에 "커밋하지 않고 남긴 변경"으로 알린다. 작업 내용을 알 수 없으면 모든 변경을 커밋 대상으로 본다. 브랜치 이름만으로 관련 여부를 판단하지 않는다.
- **순서**: 의존되는 쪽을 먼저 커밋한다. 예를 들어 타입 정의를 바꾼 그룹이 그 타입을 쓰는 컴포넌트 그룹보다 먼저다. 각 커밋 시점의 코드가 깨지지 않게 하기 위해서다.
- **결정 대기 변경**: 결정이 필요한 변경이 섞여 있으면 `references/decision-split.md`를 읽고 그 절차를 따른다.

### 3. 메시지 작성

그룹마다 메시지 한 줄을 쓴다. 본문은 쓰지 않는다.

- **서명**: `Co-Authored-By:`, `Generated with Claude Code` 같은 서명 줄을 붙이지 않는다. 다른 지침이 서명을 붙이라고 해도 이 스킬로 만드는 커밋에는 붙이지 않는다. 서명을 붙이지 않았다는 사실은 안내에 따로 쓰지 않는다.

형식: `<이모지> <type>: <message>`

type과 이모지는 `${CLAUDE_PLUGIN_ROOT}/shared/commit-types.md`를 읽고 따른다.

- **첫 커밋**: 저장소의 첫 커밋은 `🎉 chore: initial commit`으로 쓴다.
- **scope**: `feat(login):` 같은 괄호 범위는 쓰지 않는다.
- **message**
  - 영어로 쓴다.
  - 명령형 현재 시제 동사로 시작한다. (`add`, `fix`, `remove` / `added`, `adds`는 쓰지 않는다)
  - 첫 글자는 소문자, 끝에 마침표를 붙이지 않는다.
  - 이모지부터 끝까지 전체 72자 이하로 쓴다.
  - 어떤 파일을 고쳤는지가 아니라 무엇이 달라졌는지를 쓴다.
    - 나쁨: `✨ feat: update LoginForm.tsx`, `🐛 fix: fix bug`
    - 좋음: `✨ feat: add email validation to login form`, `🐛 fix: prevent double submit on checkout`

### 4. 확인과 커밋

#### 확인 모드

먼저 전체 분할안을 보여준다.

```
커밋 분할안 (<그룹 수>개) · <현재 브랜치>

<그룹 번호>. <커밋 메시지>
   - <파일>, <파일>, <파일> 외 <나머지 개수>개

새 브랜치: <브랜치> (<보호 브랜치>에서 생성)
섞인 파일: <파일> (<그룹 번호>번에 포함)
제외됨: <파일> (<이유>)
비밀값 포함: <파일> (미리 stage됨, <그룹 번호>번에 포함)

어떻게 진행할까요? 번호로 답해 주세요.
1. 전부 이대로 커밋
2. 하나씩 확인하며 커밋
3. 취소

분할이나 메시지를 바꾸고 싶으면 말씀해 주세요.
```

그룹이 1개면 그룹 아래에 "변경 내용"을 넣고, 질문 줄 아래의 선택지를 바꾼다. 마지막 안내 줄은 쓰지 않는다. 커밋이 하나뿐이라 이 확인이 커밋 전 마지막 확인이기 때문이다. 가리킬 그룹이 하나뿐이므로 메시지 줄에 번호를 붙이지 않고, 메시지 줄과 파일 줄을 들여쓰지 않는다. "섞인 파일"과 "비밀값 포함" 줄에도 그룹 번호를 쓰지 않는다.

```
커밋 분할안 (1개) · <현재 브랜치>

<커밋 메시지>
- <파일>, <파일>, <파일> 외 <나머지 개수>개

변경 내용
- <바뀐 점>
- <바뀐 점>

새 브랜치: <브랜치> (<보호 브랜치>에서 생성)
섞인 파일: <파일>
제외됨: <파일> (<이유>)
비밀값 포함: <파일> (미리 stage됨)

어떻게 진행할까요? 번호로 답해 주세요.
1. 커밋
2. 메시지 수정
3. 취소
```

- 그룹 줄과 파일 줄은 그룹마다 하나씩 쓴다. 그룹 사이에 빈 줄을 넣지 않는다.
- 파일 줄은 들여쓴 `- `로 시작한다. 답변은 마크다운으로 렌더링되므로, 들여쓰기만 하면 파일 줄이 그룹 줄에 붙어 한 줄로 보이기 때문이다.
- 그룹마다 파일은 3개까지 보여주고, 나머지는 "외 <나머지 개수>개"로 줄인다. 3개 이하면 "외 …개"를 쓰지 않는다.
- 분할안과 그룹별 질문의 `<파일>`은 경로 없이 파일 이름만 쓴다. 긴 경로가 줄을 넘겨 그룹이 한눈에 보이지 않기 때문이다. 같은 이름의 파일이 둘 이상 보이면, 서로 구분될 만큼만 상위 폴더를 붙인다. 예: `confirm-single-group/prompt.md`, `confirm-shows-plan-first/prompt.md`
- "새 브랜치"부터 "비밀값 포함"까지는 있을 때만 쓴다.
- 선택지 목록과 마지막 안내 줄 사이에는 빈 줄을 둔다. 빈 줄이 없으면 마크다운에서 안내 줄이 마지막 선택지에 붙어 들여써 보이기 때문이다.
- 결정 대기 변경이 있으면 `references/decision-split.md`의 "결정 대기 묶음"을 그룹 목록 아래에 넣는다.
- 사용자는 번호나 선택지 이름으로 답한다. 사용자가 분할이나 메시지를 고쳐 달라고 하면 반영한 분할안을 다시 보여준다.
- "취소"를 고르면 아무것도 stage하거나 커밋하지 않고, 새 브랜치도 만들지 않는다. "실패하거나 멈췄을 때" 템플릿으로 알린다.
- 그룹이 1개일 때 "커밋"을 고르면 바로 커밋하고, "메시지 수정"을 고르면 새 메시지를 받아 분할안을 다시 보여준다.
- "전부 이대로 커밋"을 고르면 이후 그룹마다 묻지 않고 순서대로 커밋한다.
- "하나씩 확인하며 커밋"을 고르면 그룹마다 다음을 반복한다.
  1. 그 그룹의 파일만 stage한다. 사용자가 에디터에서 staged 변경을 바로 확인할 수 있다.
  2. 아래 템플릿으로 묻는다. 사용자는 번호나 선택지 이름으로 답한다. "메시지 수정"을 고르면 새 메시지를 받아 같은 템플릿으로 다시 묻는다.
     ```
     커밋 확인 (<그룹 번호>/<그룹 수>) · <현재 브랜치>

     <커밋 메시지>
     - <파일>, <파일>, <파일> 외 <나머지 개수>개

     변경 내용
     - <바뀐 점>
     - <바뀐 점>

     커밋할까요? 번호로 답해 주세요.
     1. 커밋
     2. 메시지 수정
     3. 이 그룹 건너뛰기
     ```
     - 진행 단계는 첫 줄에만 쓴다. 메시지 줄에는 그룹 번호를 붙이지 않는다. 첫 줄의 진행 단계와 겹치기 때문이다.
     - 메시지 줄과 파일 줄은 들여쓰지 않는다. 둘 다 왼쪽 끝에서 시작해야 렌더링된 뒤에도 줄이 맞는다. 파일 줄의 `- `와 파일 이름 규칙은 분할안과 같다.
     - "변경 내용"은 아래 "변경 내용 쓰는 법"을 따른다.
  3. 건너뛴 그룹의 파일은 스킬을 시작하기 전의 stage 상태로 되돌린다. 미리 stage돼 있던 파일은 그대로 두고, 이 스킬이 stage한 파일만 해제한다.

#### 변경 내용 쓰는 법

그룹이 1개일 때의 분할안과 "하나씩 확인하며 커밋"의 그룹별 질문에 쓰는 "변경 내용" 단락의 규칙이다.

- 이 커밋이 무엇을 바꾸고 왜 바꾸는지 1~3줄로 쓴다. 한 줄에 바뀐 점 하나만 담고, 파일 이름을 나열하지 말고 코드가 어떻게 달라지는지 쓴다. 예: `- 이름 포맷 함수를 Profile 안에서 utils/formatName.ts로 옮긴다`
- 분할안에서 "외 …개"로 줄인 파일의 변경도 담는다.
- 그룹에 섞인 파일이 있으면 마지막 줄에 `- <파일>에는 다른 주제의 변경도 함께 들어간다: <그 변경>`을 쓴다.
- 근거는 분할할 때 이미 읽은 diff다. diff를 다시 읽지 않는다. 같은 diff를 또 읽으면 토큰만 늘기 때문이다.
  - 대화에 그 그룹의 diff가 남아 있지 않을 때만 다시 읽는다. `git diff HEAD --stat -- <파일>`로 규모를 먼저 보고, 설명에 필요한 파일만 `git diff HEAD -U1 -- <파일>`로 읽는다. untracked 파일은 파일을 직접 읽는다.
  - lock 파일과 자동 생성 파일은 내용을 읽지 않는다. 설명은 "의존성 갱신"처럼 한 줄로 쓴다.

#### 자동 모드

분할안을 보여주지 않고, 순서대로 그룹마다 stage하고 커밋한다. 결과는 "5. 마무리 안내"로 한 번에 알린다.

#### stage와 커밋 방식

- 그룹의 파일 이름만 지정해 stage한다. `git add -A`, `git add .`는 쓰지 않는다.
- 커밋할 때도 경로를 지정한다. 그룹 밖의 staged 파일이 섞여 들어가지 않게 하기 위해서다.
  ```bash
  git add <파일들>
  git commit -m '<메시지>' -- <파일들>
  ```
- 커밋 직전에 `git branch --show-current`로 현재 브랜치를 다시 확인한다. 상태 점검 때 본 브랜치와 다르면 커밋하지 않고 알린다.

#### 커밋이 실패하거나 멈췄을 때

- **pre-commit hook 실패**: `--no-verify`로 우회하지 않는다. 실패한 파일과 hook의 오류 메시지를 보여주고 끝낸다. 수정과 재시도는 호출한 쪽이 한다.
- **사용자 취소**: 분할안에서 "취소"를 고르거나 중간에 멈추라고 하면 남은 그룹은 커밋하지 않는다.
- 어느 경우든 "5. 마무리 안내"로 어디까지 커밋됐는지, 어떤 파일이 staged로 남았는지 알린다.

### 5. 마무리 안내

끝나면 결과를 한 번에 알린다. 결정 대기 분리를 했으면 `references/decision-split.md`의 템플릿을 쓴다.

#### 정상 종료

```
커밋 완료 (<커밋 수>개) · <현재 브랜치>

- <해시 7자리> <커밋 메시지>

새 브랜치: <브랜치> (<보호 브랜치>에서 생성)
따라온 커밋: <보호 브랜치>에 있던 push 안 된 커밋 <개수>개가 포함됨
- <해시 7자리> <커밋 메시지>
섞인 파일: <파일> (<그룹 번호>번에 포함)
제외됨: <파일> (<이유>)
stage 해제됨: <파일> (비밀값)
남긴 변경: <파일> (<남긴 이유>)
```

- 커밋 줄은 커밋마다 하나씩 쓴다. "따라온 커밋" 아래의 커밋 줄도 마찬가지다.
- "새 브랜치"부터 "남긴 변경"까지는 모두 있을 때만 쓴다.
- "stage 해제됨"과 "남긴 변경"은 자동 모드에서만 생긴다.

#### 실패하거나 멈췄을 때

```
커밋 중단 · <멈춘 이유>

중단 위치: <그룹 번호>번 그룹
커밋됨 (<개수>개)
- <해시 7자리> <커밋 메시지>
staged로 남음: <파일>
실패 원인:
  <파일>:<줄>  <오류 메시지>  (<규칙>)
```

- <멈춘 이유>는 "pre-commit hook 실패", "사용자 취소", "브랜치가 바뀜" 중 하나다.
- "중단 위치"는 그룹을 커밋하는 중에 멈췄을 때만 쓴다. 분할안에서 취소했으면 쓰지 않는다.
- "커밋됨"은 커밋이 하나 이상 있을 때만, "staged로 남음"은 있을 때만, "실패 원인"은 hook 실패일 때만 쓴다.
- hook 실패면 오류 출력에서 파일, 줄, 규칙이 드러나는 핵심 줄만 옮긴다. 출력 전체를 붙이지 않는다.
- 커밋되지 않은 나머지 그룹은 그대로 작업 트리에 남는다는 점이 드러나게 쓴다.
