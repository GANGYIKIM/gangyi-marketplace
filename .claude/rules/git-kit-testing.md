# git-kit 테스트 규칙

## 어떤 테스트를 쓰나

- `plugins/git-kit/evals/` (`claude plugin eval`): GitHub 없이 끝나는 흐름. eval sandbox는 네트워크와 unix 소켓을 막는다.
- `plugins/git-kit/gh-evals/`: GitHub이 필요한 흐름. 진짜 `gh`와 가짜 GitHub 서버로 돌린다. 쓰는 법은 `gh-evals/README.md`.
- 실제 GitHub(테스트용 저장소): 아래 "실제 GitHub에서 확인할 때"에만 쓴다.

## 몇 번 돌리나

- 문구나 채점 패턴만 바뀐 좁은 수정, 작업 중 확인: 1회
- 규칙의 동작이 바뀐 수정의 마지막 확인: 바뀐 곳을 거치는 케이스는 3회, 나머지 관련 케이스는 1회
- 실패하거나 결과가 애매하면 그 케이스만 더 돌린다.
- 여러 번이나 여러 케이스를 돌릴 때는 `-j`로 동시에 돌린다. 동시에 돌리는 실행은 같은 사용 한도를 함께 쓴다.

## 채점

- regex 채점을 먼저 쓴다. LLM judge는 regex로 볼 수 없을 때만 쓴다.
  - judge는 기본으로 haiku이고, 한 단어(PASS/FAIL)로 답하게 해 3표 다수결로 정한다. 응답에 FAIL이라는 단어가 있으면 FAIL 표로 센다. 판정 이유는 결과 파일에 남지 않는다. 정상 출력에 FAIL을 준 적이 있다.
- 정확해야 하는 것(선택지 번호와 이름, 기록과 보고서 형식, 값)은 글자 그대로 채점한다. 모양만 정한 것(정보 줄의 라벨, 들여쓰기, 빈 줄)은 라벨과 값이 있는지만 본다.
- 없어야 하는 것은 `match: not_contains`로 본다.
- `target: trace`에는 스킬 문서 본문도 들어간다. 템플릿 글자가 아니라 실제로 채워진 값(예: `PR 생성 보류 ·`)으로 찾는다.

## 실제 GitHub에서 확인할 때

- 언제
  - 보고서와 본문이 GitHub 화면에서 어떻게 보이는지 바뀔 때 (WARNING·NOTE 상자, 각주, 체크박스)
  - 권한, 브랜치 보호, 머지 뒤 브랜치 자동 삭제처럼 GitHub 쪽 동작에 기대는 규칙을 바꿀 때
  - git-kit이 새 gh 명령을 쓰거나 gh 버전을 올렸을 때. gh-evals의 가짜 서버가 실제와 같은지 확인한다.
- 어떻게
  - `claude --plugin-dir <git-kit 경로>`로 연다. 시나리오마다 새 대화에서 시작한다.
  - 머지, 브랜치 삭제, Draft 해제는 사람이 한다.
  - 확인한 것과 결과는 그 변경의 PR Testing에 쓴다.
- 대표 흐름 (필수가 아닌 예시. 바꾼 것에 맞춰 고른다)
  - 일반 PR: "PR 만들어줘" → 확인 질문과 미리 보기 → PR 생성 → 커밋을 더하고 다시 갱신해 보고서 코멘트 하나만 고쳐 쓰는지
  - 결정 대기 PR 처음부터 끝까지: 결정 대기 분리 → 🚧 Draft PR → PR에서 답 체크 → 확정 → 반영 커밋과 PR 갱신 → 마무리
  - 쌓인 결정 대기 PR: 결정 마무리 뒤 Draft 유지 → 사람이 아래 PR 머지 → base 변경과 Draft 해제
